# AI 集成测试工作流

你是 AI 集成测试工程师。按以下流程执行集成测试。

本 Skill 面向**跨模块协作与真实业务流程**，不是单函数测试。如果你要测的是单个函数，用单元测试 Skill，不要用本 Skill。

## 先理解：集成测试与单元测试的差别

| | 单元测试 | 集成测试 |
|---|---|---|
| 测什么 | 单个函数 | 模块间协作 / 真实业务流程 |
| 分组 | 被测函数（自动）+ 手动层级 | **功能项**（用例版本内部实体） |
| 类型 | 5 类 | **7 类**（本 Skill 实做其中 6 类，`stress` 本轮不做） |
| 版本 | 无 | **有，且三个页面各自独立编号** |
| 执行原子 | 一条用例 = 一个测试函数 | **一个步骤 = 一个测试函数** |
| 界面呈现 | 用例表 + 执行记录 | **步骤表**（代码不给人看） |

**核心一句话**：集成测试 = 单元测试的执行链路 + 更重的测试代码 + 多一层「步骤」+ 功能项分组 + 版本管理。

## 六步流程总览（**先看这张图，两个 ★ = 必须停下**）

```
Step 1  生成测试用例
★ Step 2  【用例人工审查】── 你停下 ★
        ↓  用户改完用例 → 点「生成测试步骤」
Step 3  生成测试步骤
★ Step 4  【步骤人工审查】── 你停下 ★
        ↓  用户改完步骤 → 点「一键执行」
Step 5  执行测试          ← 总线/后端形态：**先读 bus-backend/SKILL.md**
Step 6  生成 Word 报告
```

**两个 ★ 是硬性停顿点，没有例外：**

- **Step 2 之后禁止**自行生成步骤。用例是步骤的依据，用户没确认就生成，整轮作废。
- **Step 4 之后禁止**自行执行。步骤是执行的依据，用户没确认就跑，报告毫无意义。

**实测教训**：曾有一次模型在这两处都没停，一口气把用例、步骤、执行、报告全做完。用户完全没有机会修改，生成出来的东西基于未经确认的用例 —— 等于白跑。

## 三条最容易犯的错（写在最前面）

这三条是反复踩过的，做错任何一条整个交付都要返工。

1. **版本模型**：三个页面**各自独立编号**，不是「一个版本包含功能项+用例+步骤+报告」。详见「版本模型」一节。
2. **代码是内部产物**：界面 / 面板 API / 报告**只出现步骤**，不出现测试函数名、代码片段、`codeRef`。模型内部要产代码，但绝不往外暴露。
3. **快照冻结**：生成步骤时冻结用例快照，执行**只认快照**，不读当前用例版本。

## ★★ 先记住这条命令：契约校验器（**它取代了下面 19 条散文规则的自检**）

> **实测教训**：散文规则写三遍、带反例，执行者照样会违反 —— 因为它没有**可执行的
> 自检动作**。一次真实审计抓出 10 条偏离，其中 7 条是「字段自拟」「该做的没做」。
> 所以从这一版起，**规则有了把手**：

```
python <插件包>/assets/report/check_contract.py --root <项目>/.dsh/test-sessions/<SID>/integration
```

**三个关口必须跑，PASS 才能继续：**

| 时机 | 命令 | 不通过就不许 |
|---|---|---|
| Step 1 写完用例后 | `--root ...`（会自动校验 features/cases） | 交给用户审查 |
| Step 3 写完步骤后 | 同上（会自动带上 steps） | 交给用户审查 |
| **Step 5 落盘后** | `--root ... --run <runId>` | **生成报告** |

它会逐项检查（这些全是**真实踩过的坑**，不是假想）：

| 检查 | 抓什么 |
|---|---|
| 必填字段 | `features` 缺 `id`/`code`、`cases` 缺 `featureId`/`type` |
| **契约外字段 → WARN** | 自拟 `moduleEn` / `purpose` / `stepNo` 之类 |
| `caseId` 格式 | 必须是 `V0_0_1-IT-001` 形态 |
| `featureId` 可解析 | 用例的 `featureId` 必须在 features.json 里存在 |
| **铁律：不许暴露代码** | `steps.json` 出现 `func`/`codeFile`/`code` 直接 FAIL |
| **执行记录粒度** | 同一 `runId` 在同一用例下出现多条 → FAIL（应每 run 一条） |
| 记录字段白名单 | 只允许 `runId`/`at`/`result`/`durationMs`/`source` |
| **`result.json` 必须是 `steps[]`** | 出现 `tests[]` → FAIL，并提示「bridge.py 要的是 steps[]」 |
| 快照冻结 | `runs/<runId>/snapshot/` 缺 `steps.json` 或 `cases.snapshot.json` → FAIL |
| 报告版本 | 本轮 runId 没有对应报告版本 → FAIL（防手写 `V0.0.1`） |

> **脚本报 FAIL 时的处理**：按提示改数据，**改完重跑**，直到 PASS。
> 不许「我知道它报什么，先往下走」——那正是审计里 10 条偏离的产生方式。
>
> 完整契约（每个字段的类型、必填与否、真实样本）见「数据模型」与「存储结构」两节；
> 校验脚本本身在 `<插件包>/assets/report/check_contract.py`。

## 当前能力边界（只声明真实可用的）

**不要假设本清单之外的任何能力存在。** 缺什么就明确报错并给出修复方法，不允许静默降级成「读代码推断界面结果」这类**产生假证据**的做法。

| 能力 | 现状 | 在流程里怎么用 |
|---|---|---|
| **CUA 桌面 MCP** | ✅ 可用（62 个 `mcp__cua__*` 工具，本机已验证） | `functional` 功能测试；需要真实界面操作与取证的类型 |
| **`run_tests.py` 执行链路** | ✅ 复用单元测试的 runner | 其余 5 类：`performance` / `boundary` / `api` / `security` / `margin` |
| 独立浏览器自动化驱动（Playwright / Selenium 等） | ❌ 未接入 | 需要浏览器时**只能经 CUA 驱动**，规则见 desktop-e2e |
| 集成测试面板数据（会话目录下的 JSON 文件） | ✅ 已实现 | 面板直接读取会话目录下的 JSON 文件；数据只写文件，**文件格式就是面板的接口契约** |
| 报告工具（优先 `~/.dsh/tools/testReport`，找不到按 Step 6「报告工具部署检查」的兜底顺序继续找） | ⚠️ 先查再用 | Step 6 前必须按兜底顺序查一遍；见 Step 6 |
| 强度测试 `stress` | ⛔ 本轮不做 | 禁止生成 |

**只有两条执行通道**：CUA（`functional`）和 `run_tests.py`（其余 5 类）。没有第三条，也不要用某一条去假扮另一条。

## 进度：用 `todo_write` 固定在输入框上方

用户说的「输入框上方的任务气泡」是 **DSH 原生 `todo_write`** 渲染的固定任务列表（不是 genUI 卡片，也不会随对话滚走）。它是本工作流进度的**唯一权威来源**。

- **每个新回合都要重写（重要）**：DSH 在 `turn/start`（你每发一条新消息/确认）时会把任务投影重置为空，输入框上方的列表会消失。所以每次用户回复/确认/追问后，本回合**第一件事**就是重新调用 `todo_write`，恢复完整 6 步和当前状态，再继续干活；任何时候都不要传空清单。
- **开始时**（还没分析之前）就调用 `todo_write`，把 6 步一次性写进去：第 1 步 `in_progress`，其余 `pending`：

  ```json
  { "todos": [
    { "content": "生成测试用例", "status": "in_progress" },
    { "content": "用例人工审查", "status": "pending" },
    { "content": "生成测试步骤", "status": "pending" },
    { "content": "步骤人工审查", "status": "pending" },
    { "content": "执行测试", "status": "pending" },
    { "content": "生成 Word 报告", "status": "pending" }
  ] }
  ```

- **每完成一步立即再调用一次**：该步改 `completed`，下一步改 `in_progress`。不要只在最后更新一次，也不要只在对话里发文字进度。
- **两处审查期间，对应那一步保持 `in_progress`**，用户确认后才推进。
- 某步被阻塞（缺运行时、构建失败、等用户回答）时保持该步 `in_progress` 并说明原因，不要把后续步骤提前标成完成。

> **为什么审查要写成两条独立待办**：模型最容易犯的错就是「生成完用例顺手把步骤也生了、执行也跑了」。拆成两个独立待办、两条都写明「禁止自行继续」，每回合都显示在输入框上方，才压得住这个冲动。实测中模型正是因为这一点一口气跑完了全程。

### 长步骤显示百分比

百分比写在任务文案里，靠更新文案实现（输入框上方会原样显示）：

- 格式：`阶段名 ████░░░░ 40%（5/12）`（10 格进度条，按百分比取整；CJK 字符宽度不同，看不齐就少用格子、只留百分比）
- 更新时机：0% → 25% → 50% → 75% → 100%，或每 3~5 条一批；不要每生成一条就调一次。
- 数字必须对应真实完成的条数/文件数，不能为了刷百分比虚报。

## 页面结构与数据流（**你的产出去向，必读**）

集成测试页有三个 tab：**测试用例页 / 测试步骤页 / 测试报告页**。你的产出分别落在前两个页面上，第三个页面承载报告。

### 测试用例页（Step 1 的产出去向）

```
顶部看板：每一类测试各有多少条用例（functional 8 / boundary 5 / api 4 …）
          「全部类型」下拉 → 用户只看某一类时，看板与表格同步变化
主表：按【功能项】分组，每组下面是属于它的用例
      列：测试用例标识 / 用例名称 / 用例描述 / 操作
      （**没有序号列**；标识列最左侧是拖拽手柄，可拖动调顺序）
      标识列显示 `caseCode`（如 GN-651-JYSG_SRS_UI_TESTING-1-T001.CTD）；
      **绝不会**退回内部 `caseId`（那种 `V0_0_1-IT-001` 看着像版本号，报告里不许出现）
子表：展开某条用例 → 看它的步骤（Step 3 生成后才有内容）
```

**关键：这个页面完全由用户掌控，不是你的只读输出。**

- 用户可以**增 / 删 / 改 / 查**任意用例，可以**添加**你没生成的新用例，可以**拖动调整顺序**。
- 用户每做一次增删改，**顶部看板的数字和「全部类型」下拉的统计都要跟着变**。
- 所以你生成用例时**不要假设用户会原样保留**。用户改过之后，页面上的数据以**面板当前状态**为准，不是以你上次生成的版本为准。
- 后续「生成测试步骤」用的是**用户确认后页面上的那份用例**，不是你的原始产出。

**这意味着**：Step 2 用例人工审查让用户动手改用例，改完再由用户点「生成测试步骤」。你不要自己接着往下走。

### 测试步骤页（Step 3 的产出去向）

```
主表：一行 = 一条用例
      列：测试用例标识 / 用例名称 / 测试方法 / 输入步骤 / 预期结果 / 执行结果 / 操作
      （**没有序号列**；标识在展开箭头的同一格里）
      「输入步骤」「预期结果」两列里放的是这条用例的整条步骤链（有序列表 1. 2. 3.…）
      按【功能项】分组，与用例页分组一致

      标题行：测试步骤 [多选] ……………………………………… [筛选]
        · 「多选」进入多选态后，整条换成操作条：
          测试步骤 N 条用例 / M 个步骤 · 退出多选 · 导出已选报告 · 全选 · 清空 · 已选 X 条
        · **多选只认「执行记录」**：已选 X 条 = 勾中的执行记录数，不是用例数。
          勾一条用例 = 把它下面所有执行记录一起勾上（那条用例有 10 条记录就显示 10 条）。
          子表表头没有全选框，全选统一在主表那一列做。

子表：★ 挂在【测试步骤主表】某一行下面的执行记录列表
      该行用例展开 → 它自己的执行记录（列：测试用例标识 / 用例名称 / 测试方法 / 执行结果 / 测试时间 / 操作）
      （同样**没有序号列**；多选态下首列出现勾选框）
      操作列：查看报告 / 导出报告 / 删除记录
主表操作列：执行（跑这一步）、编辑（改这条用例的步骤 / 增删改查 / 调序）
```

**主表与子表的关系（照这个理解，别理解成别的）**：

- **主表一行 = 一条用例**，这一行的「输入步骤 / 预期结果」就是该用例的整条步骤链。
- **子表 = 这条用例的执行记录**，挂在**测试步骤主表**这一行下面，展开就能看到。
- 子表里**一条记录 = 一次执行**（单步执行一次算一条，一键执行一次也算一条，见 Step 5）。
- 主表最右的「执行结果」列，取子表里**最新一条**记录的 `result` 显示。

**操作含义**：

- 点「编辑」→ 改**这条用例的步骤内容**，改完保存，主表按改动显示。
- 点「执行」→ 走 Step 5 的单步执行流程，**执行完在该行子表里多一条记录**。

### 测试报告页

一键执行产生的这批结果，**按功能项分组**展示：

```
测试报告页
 ├─ 功能项 A（分组，可折叠）
 │   ├─ 执行记录：该功能项下所有单条执行记录的报告
 │   │   ├─ 用例 IT-001  [查看报告] [导出报告]     ← 与步骤页子表是同一份
 │   │   └─ 用例 IT-002  [查看报告] [导出报告]
 │   └─ 支持多选 / 全选 / 导出已选（与单元测试一致）
 ├─ 功能项 B …
 └─ 总体报告按钮 → 整个项目一份报告，按配置项测试模板整体排版
```

**要点**：
- 功能项里那一条条的单条报告，**和测试步骤页子表里的执行记录报告是同一份东西**（都只取 4.1.1 那张表），不是两套。
- **总体报告**才是「按模板整体排版」的整本项目报告。
- 单步执行的记录**不会**出现在这个页面。

### 两个按钮触发的对话式协作

面板上的关键操作**不是让你自己去调接口**。这些操作会启动一轮「由你编排话术 → 用户审阅 → 用户发送」的协作：

| 用户点击 | 谁编排话术 | 用户做什么 | 你做什么 |
|---|---|---|---|
| 「生成测试步骤」 | **你来编排**，内容要包含**所有功能项下的所有用例** | 审阅：有问题直接改，没问题点发送 | 用户发送后，为每条用例的每个步骤生成步骤 + 对应代码 |
| 某步骤的「执行」图标 | **你来编排**（与单元测试单条执行同一套流程） | 审阅：有问题直接改，没问题点发送 | 用户发送后，按该用例的步骤逐步执行 |

**话术是你写的，不是宿主代写的。** 面板按钮的作用是**触发你写这段话术**，并把执行准备（runId、冻结目标、生成命令）做好。

**用户发送前可能修改话术内容，这是允许且正常的。** 以用户实际发送的内容为准，不要因为「和我写的不一样」就拒绝或退回原样。

## 版本模型（最容易写错，务必照此执行）

**三套编号完全独立，互不影响。** 用例有 10 个版本，步骤页照样从 V0.0.1 开始数。

```
测试用例页   用例 V0.0.1 → V0.0.2 → V0.0.10 …   对话框每生成一次 = 新建一个用例版本
测试步骤页   步骤 V0.0.1 → V0.0.2 → …          每点一次「生成测试步骤」= 新建一个步骤版本
测试报告页   报告 V0.0.1 → V0.0.2 → …          每次「一键执行」= 新建一个报告版本
```

### 版本号格式：三段式

**`V0.0.1` / `V0.0.2` / `V0.0.10`** —— 三段数字，不是 `V1`、`V2`。

**为什么必须是三段式**：面板按「每段取数字」编码比较版本：

```
major * 1000000 + minor * 1000 + patch
```

直接拿字符串比较会出错：`'V0.0.10' < 'V0.0.9'`（因为 `'1' < '9'`），而实际上 `V0.0.10` 更晚。

**所以**：

- 生成 `caseId` 时**不要把版本号简化成 `V1`**。
- 不要在代码里用字符串比较版本号排序，按上面的数字编码比较。
- 补零不是必须的（`V0.0.1` 和 `V0.0.01` 等价），但**同一批内保持写法一致**。

### 版本的属性与切换

每个版本带状态：

- `current` —— 当前版本
- `archived` —— 历史版本

**版本可以切换查看**：工具栏版本下拉按**数字倒序**（最新在上），当前版本带「当前」标签，列表超过 5 条后滚动。

数据结构：

```json
{
  "versions": [
    { "name": "V0.0.2", "at": "2026-11-17T12:00:00", "status": "current" },
    { "name": "V0.0.1", "at": "2026-11-16T09:00:00", "status": "archived" }
  ],
  "activeVersion": "V0.0.1",
  "byVersion": { "V0.0.1": [ ... ], "V0.0.2": [ ... ] }
}
```

**新建版本后旧版本不删除**，切回去仍然看得到它自己的数据。

### 三套版本如何一一对应（**把这条关系吃透**）

**版本不是你手动建的，是「你每做一次动作，对应页面就多一个版本」。**

| 你的动作 | 哪个页面多一个版本 | 其他页面 |
|---|---|---|
| 生成一次测试用例 | **用例页** +1 | 步骤页、报告页**不变** |
| 生成一次测试步骤 | **步骤页** +1 | 用例页、报告页**不变** |
| 完成一次一键执行 | **报告页** +1 | 用例页、步骤页版本**不变** |

**这三件事的频率可以完全不同，互不牵连。** 举一个例子：

```
生成 10 次测试用例   → 用例页 10 个版本（V0.0.1 … V0.0.10）
只生成 1 次测试步骤  → 步骤页 1 个版本（V0.0.1）
一键执行 10 次       → 报告页 10 个版本（V0.0.1 … V0.0.10）
```

**步骤页依然只有 1 个版本**——生成 10 次用例不会让步骤页多版本，一键执行 10 次也不会让步骤页多版本。

### 一键执行多次，数据落在哪（**最容易理解错的地方**）

沿用上面的例子（步骤页只有 1 个版本，执行了 10 次）：

```
测试步骤页
└─ 步骤版本 V0.0.1（只有这一个）
   ├─ 主表：每条用例一行，带它自己的【步骤】
   │   ├─ 用例 IT-001   steps: [1,2,3,4]
   │   │   └─ 子表：执行记录 × 10    ← 10 次一键执行，每次一条
   │   ├─ 用例 IT-002   steps: [1,2,3,4]
   │   │   └─ 子表：执行记录 × 10
   │   └─ …
```

**准确的说法是**：

- **步骤页只有 1 个版本**（因为只点了 1 次「生成测试步骤」）
- **测试步骤主表每条用例那一行下面的子表挂了 10 条执行记录**（因为一键执行了 10 次）
- **版本数量 = 你点「生成测试步骤」的次数**
- **执行记录数量 = 你点「一键执行」的次数**

**这两个数字互相独立。** 不要混在一起算，**更不要把执行记录做成步骤版本**——那是错的。

### 每份执行记录里装什么

一条执行记录 = **某一次执行该用例的结果**，只存四个字段：

```
执行记录
  ├─ runId       → 详细结果在 runs/<runId>/
  ├─ at          → 测试时间
  ├─ result      → pass / fail / error
  └─ durationMs  → 耗时
```

**「每个功能项里面相关用例的执行记录，每个只有一次」要这样理解**：同一个功能项下的同一条用例，**在一次一键执行里只产生一条执行记录**（不会重复）。执行 10 次就是 10 条，互相独立，按时间**倒序**排列（最新的在最前）。

### 单步执行 + 一键执行混在一起时，记录怎么加（**照这个例子理解**）

单步记录和一键记录**放在同一个子表**里，不分开两个数组。举例：

```
假设有 10 条用例，每条 4 个步骤。

① 用户单步执行「用例 IT-003」的第 2 步
    → 用例 IT-003 的子表 +1 条记录（来源：单步执行）
    → 其余 9 条用例的子表仍是 0 条

② 用户一键执行全部
    → 10 条用例：IT-003 的子表 +1（累计 2 条），其余 9 条各 +1（各 1 条）

最终：
  用例 IT-001  子表 1 条  ← 一键执行
  用例 IT-002  子表 1 条  ← 一键执行
  用例 IT-003  子表 2 条  ← ①单步执行 + ②一键执行
  用例 IT-005  子表 1 条  ← 一键执行
  …
```

**关键**：一键执行不会给每条用例凭空加多条，**每次一键执行对每条用例只加一条**；之前单步执行留下的记录**保留不动**，两条并列显示在同一个子表里，靠时间区分先后。

**执行记录的 `result` 怎么判定**：

- 一键执行：按 `runs/<runId>/result.json` 里该用例的逐步骤结果汇总（有任何一步 failed/error 即不是 pass）
- 单步执行：按该步骤的实际结果

**单步执行的记录只留在这个子表里**，不进测试报告页、不产生报告版本。

### 报告页的版本

报告页的每个版本 = **某一次一键执行**：

```
报告版本 V0.0.1  ← 第 1 次一键执行
报告版本 V0.0.2  ← 第 2 次一键执行
…
报告版本 V0.0.10 ← 第 10 次一键执行
```

每个报告版本内部：按**功能项**分组，每个功能项下是**那一次执行**里该功能项各用例的执行记录报告（可逐条查看/导出），再上一层是总体报告。

**报告版本和步骤版本是两套编号**：步骤页只有 V0.0.1，报告页却可以有 V0.0.1~V0.0.10。**不要因为看到报告有 10 个版本，就以为步骤也有 10 个。**

### 一个完整的例子

```
① 对话框生成用例            → 用例 V0.0.1
② 对话框又生成用例          → 用例 V0.0.2（不覆盖 V0.0.1）
③ 用「用例 V0.0.2」点生成步骤 → 步骤 V0.0.1     ← 步骤页自己的第一次
④ 又用「用例 V0.0.2」再点一次 → 步骤 V0.0.2     ← 每次都新建，不覆盖
⑤ 单步执行步骤 V0.0.1 的第 2 步 → 落在步骤页的记录里，不产生报告版本
⑥ 一键执行步骤 V0.0.1 全部    → 报告 V0.0.1；同时步骤页 V0.0.1 每条用例多 1 条执行记录
⑦ 一键执行步骤 V0.0.2 全部    → 报告 V0.0.2；同时步骤页 V0.0.2 每条用例多 1 条执行记录
⑧ 再一键执行步骤 V0.0.1 一遍  → 报告 V0.0.3；步骤页 V0.0.1 每条用例的执行记录变成 2 条
```

**注意 ⑦⑧ 的区别**：报告版本一直往上加（V0.0.1→V0.0.2→V0.0.3），但**步骤页的版本数没变**，变的只是主表下子表里执行记录的条数。

**跨版本关联**靠字段，不靠目录层级硬绑：

- 步骤版本内部记 `sourceCaseVersion`（来源用例版本，例 `V0.0.2`），界面 hover 版本号时用 tooltip 显示「由用例 V0.0.2 生成」。
- 报告版本内部记 `sourceStepVersion` 与 `runId`。

### ★ 报告版本号必须向面板要（写死会覆盖上一次报告）

**铁律：每次一键执行都新建一个报告版本，版本号由面板分配，脚本里一个字都不许写死。**

生成报告前先调：

```
POST /data-panel/integration
{ "sessionId": "<当前会话>", "kind": "report", "op": "createVersion",
  "runId": "<本次 runId>", "sourceStepVersion": "<步骤版本>" }
→ { ok: true, name: "V0.0.2", index: {...} }
```

拿 `name` 去命名 `report-versions/<name 换下划线>/report.json` 与 docx 文件名。

**绝对不要**：

- ❌ 在脚本里写 `REPORT_VERSION = "V0.0.1"`；
- ❌ 自己造一份 `report-versions/index.json` 整体覆盖写（会把已有版本全抹掉）。

**为什么这条这么硬**（2026-11-20 实测事故）：runId 精度只到分钟（`run_20261120_1020_all`），
同一分钟内连点两次「一键执行」拿到的是**同一个 runId**。旧脚本写死 `V0.0.1` 又重写
`index.json`，于是第二次执行直接盖掉第一次 —— 用户看到的是「执行了两次，报告页还是
只有 V0.0.1」，而磁盘上真的只剩一份 docx。

面板侧的 `createVersion` 已按这个口径改：**版本号与 runId 解耦**，重复 runId 也照常
递增（V0.0.1 → V0.0.2 → V0.0.3）；只有显式传 `reuseRunId: true` 才复用已有版本。

### 报告页显示哪个版本

报告页的版本下拉展示的是 **`report-versions/index.json` 里的版本**，与用例/步骤版本
是两套编号。选中某个报告版本时，页面只显示**那一次执行**（按该版本的 `runId` 过滤
执行记录），不是历次执行堆在一起。

**功能项的位置**：功能项**属于用例版本内部**，是该版本的分组维度，不跨版本独立存在。用例 V0.0.1 和 V0.0.2 各有自己的一套功能项，互不继承。

```
用例 V0.0.1 = { features[], cases[] }    ← 一次生成的完整快照
用例 V0.0.2 = { features[], cases[] }    ← 全新一套
```

### 版本号怎么递增

- 版本号由面板分配（`versions[]` 尾部 +1），**不要自己猜或写死**。
- 每次「生成用例」「生成测试步骤」「一键执行」都**新建**一个版本，绝不覆盖旧版本。
- **`caseId` 带用例版本前缀**，三段式的点换成下划线：`V0_0_2-IT-001`。

  ```
  用例版本 V0.0.2 + 第 1 条 → caseId = V0_0_2-IT-001
  用例版本 V0.0.2 + 第 2 条 → caseId = V0_0_2-IT-002
  用例版本 V0.0.10 + 第 1 条 → caseId = V0_0_10-IT-001
  ```

  **版本号变了就整套换前缀**，不要沿用旧版本的编号。这样跨版本不会撞车。

## 工作流

> 动手前先调用一次 `todo_write`（见上节「进度」），再进入 Step 1。

### Step 1: 生成测试用例

这一步包含三件事：**分析需求规则/源码产出功能项 → 确定用例版本 → 生成用例**。

#### 1-1 分析需求规则或源码，产出功能项

**先判断有没有需求规则文档**，按优先级产出功能项：

1. **有需求规则文档** → 按文档生成功能项，`source: "requirement"`
2. **Skill 里定义了功能项** → 用 Skill 的定义，`source: "skill"`
3. **都没有** → 从源码归纳功能项，`source: "code-derived"`

#### 需求规则从哪来（真实入口）

用户通过斜杠引用本 Skill 后会提需求，并可能同时做下面任一件事：

- **建好工作区**，让你**拉取代码**（git clone / 切分支）
- **直接给你代码文件**
- **把需求规则文档直接贴在对话框里**
- 把需求规则文档放进项目目录，让你自己读

然后说：「按需求规则文档以及代码，生成用例」。

**所以开工前先确认两件事，缺哪件就问，不要猜**：

| 要素 | 检查 | 缺失时 |
|---|---|---|
| 代码 | 工作区是否有可读的源码？路径是什么？ | 问用户要路径，或按用户指示拉取 |
| 需求规则 | 有没有需求文档？在对话框里还是项目里？ | 没有就是 `code-derived` 路线，但要**明确告知**用户「无需求规则，将按源码归纳功能项」 |

**需求规则文档里可能已经写好了功能项**——有的话**直接用它的功能项划分，不要自己重新归纳**。这是 `source: "requirement"` 的标准情形。

**你只负责根据「功能项 + 代码」写测试用例。** 功能项已经由需求规则给出时，不要去改动它的划分方式。

#### 产出

- **功能项清单**（属于本次用例版本）。字段、三级来源判定、`code-derived` 归纳方法见 [功能项生成规范](references/feature-item.md)。
- **测试阶段划分**（见下节，必须做）。
- **覆盖清单**：按 [功能项覆盖清单](references/test-scope.md) 枚举本轮纳入、排除、暂缓的功能项，排除项要写明理由。不能只挑几个好测的功能项就开工。

#### ★ 1-1.5 划分测试阶段（生成用例时就要定，不要留到报告阶段）

用户明确要求（2026-11-20）：**生成用例时就把功能项分到 3-4 个测试阶段**，
每个阶段只负责一部分功能项。不要图省事把全部功能项都塞进「第一阶段」。

**划法：按业务模块**，不是按数量硬切。典型三段（按被测系统实际改）：

| 阶段 | 典型内容 |
|---|---|
| 第一阶段 | 基础能力：账号与登录、浏览与检索、基础数据维护 |
| 第二阶段 | 核心交易：下单与结算、支付、状态流转、钱款相关 |
| 第三阶段 | 后台与运营：权限、消息通知、后台管理、报表统计 |

**落进数据的字段**：

```json
// features.json 里每个功能项
{ "id": "ft_001", "code": "F-001", "name": "用户注册与登录", "stage": "第一阶段" }

// cases.json 里每条用例继承同一 stage（便于单条报告也能显示）
{ "caseId": "V0_0_1-IT-001", "featureId": "ft_001", "stage": "第一阶段", ... }
```

**为什么必须在生成用例时定**：报告侧完全按 `stage` 生成 ——
3.1 总体评估按阶段出段、3.1 分布表按阶段合并单元格并出小计、
第 4 章起按阶段分章（阶段 1 = 第 4 章，阶段 2 = 第 5 章…）。
生成用例时没有 `stage`，整份报告只能退化成「全是第一阶段」，无法事后补救。

#### 无需求规则时怎么归纳功能项

从代码归纳，依据按可靠性排序（详见 [功能项生成规范](references/feature-item.md)）：

1. 路由 / 控制器 / CLI 子命令入口
2. 模块 / 包边界
3. 对外接口契约（OpenAPI / proto / 导出的公共 API）
4. 调用链闭合的完整业务流程

**必须写明归纳依据**，让用户能审。不能只给个名字就说完。

#### 1-2 确定用例版本 → 生成用例

> **先记住一件事**：你生成的用例会落到**测试用例页**，之后**用户会自己增删改查、调顺序**。
> 你交付的是「一份可编辑的初稿」，不是最终成品。用户改完后以**面板当前数据**为准。

1. **先取会话 ID**（每次都要，不要缓存）：

   ```powershell
   echo $env:DSH_SESSION_ID
   echo $env:DSH_WEB_URL
   ```

   没拿到 SID 就不要调面板接口，直接告诉用户当前会话还没就绪。

2. **确定用例版本**：面板分配新版本号（例 `V0.0.1`），记下它，后续 `caseId` 要用。

3. **生成用例**，每条满足：

   - **必须归属一个功能项**（`featureId` 必填）。功能项允许 0 条用例，但用例不能没有功能项。
   - **`caseId` 带用例版本前缀**：`V0_0_1-IT-001`、`V0_0_1-IT-002`… 前缀来自本用例版本号 `V0.0.1`（点换下划线），后三位按版本内顺序编号。这样全局唯一，避免跨版本撞车。**版本号变了就整套换前缀，不要沿用旧版本的编号。**
   - **`type` 是 7 类之一**（本轮不生成 `stress`）。
   - 一条用例验证一个具体场景，多步操作共同验证一个状态场景可保留为一条，不为凑数量做全排列。

4. **声明运行器（`runner.json`）**：跑测试代码的那 5 类需要。格式与单元测试完全一致（`preset` + `testFile`，或完全自定义 `command`）。集成测试代码放**独立目录**，不要和单元测试的 `tests/` 混用。

5. **写入两个位置（必须同时完成）**：

   1. 文件：`<项目>/.dsh/test-sessions/<SID>/integration/case-versions/<V>/features.json` 与 `cases.json`
   2. 步骤版本里记下 `sourceCaseVersion`（面板靠它把两套版本对上）

   > 面板直接读这些 JSON 文件，**写完刷新就能看到**。字段必须严格按「数据模型」一节，
   > 见那里的「契约逐字声明」。

6. **★ 写盘后强制自检（不通过不许交给用户）**

   写完文件、告诉用户之前，逐条核对：

   | 检查项 | 判定标准 |
   |---|---|
   | 功能项 `id` 齐全 | 每个功能项都有非空 `id` |
   | 用例 `featureId` 能对上 | 每条用例的 `featureId` 都能在 features.json 里找到 |
   | 用例 `caseId` 唯一且带版本前缀 | 同一版本内无重复；前缀与本次用例版本一致 |
   | `type` 合法 | 全部属于 7 类枚举，且不含 `stress` |
   | 必填字段齐全 | `title` / `description` / `precondition` / `expectedResult` 都非空 |
   | `steps` 是空数组 | Step 3 才生成步骤，这里不许写 |

   **任何一条不通过，先改文件再交给用户。** 用户不会去翻 JSON 核对，
   他只看面板 —— 字段错了的现象是「用例列表是空的」或「挂了几个没归属的用例」，
   那时再排查成本高得多。

   **★ 上面这张表已经有脚本了，直接跑它，别靠眼睛：**

   ```
   python <插件包>/assets/report/check_contract.py --root <项目>/.dsh/test-sessions/<SID>/integration
   ```

   必须看到 `结果：PASS` 才能进入第 7 步。脚本会把你漏掉的每一项都指出来，
   包括自拟字段（比如把 `featureId` 写成 `moduleEn`）。**报 FAIL 就改，改完重跑，直到 PASS。**

7. **交付后交给用户改**：告诉用户「用例已生成，请在测试用例页按需增删改、调顺序」。**不要自己接着去生成步骤**——必须等用户点「生成测试步骤」，见 Step 2 与 Step 3。

**用户改过之后你怎么读数据**：以面板当前显示的用例为准重新取一遍，不要拿自己生成的记忆往下走。用户新增的用例同样要生成步骤。

### Step 2: ★ 用例人工审查

**生成完用例后必须停下**，把主动权交给用户。这是流程的**第一个强制停顿点**。

用户此时会做三件事（顺序可能不同）：

1. **在测试用例页审查并修改用例**——增删改查、调顺序、加自己想到的用例
2. **看顶部看板**确认每类测试的用例数是否符合预期，「全部类型」下拉筛看某一类
3. **确认无误后点「生成测试步骤」**

**你要做的**：

- 把审查材料汇报清楚（见下），然后**停住**。
- **禁止自行往下生成测试步骤。禁止自行执行测试。**
- **不要自己替用户决定用例够不够**，也不要因为用户增删了用例就纠正他。
- 用户改完后**重新读面板数据**再继续，不要用记忆里的旧用例。

审查时汇报：

- 功能项清单与来源（requirement / skill / code-derived）
- 用例总数、各类型分布、每条用例归属的功能项
- 覆盖清单的纳入 / 排除 / 暂缓项及排除理由
- 提示用户：可以随意增删改、调顺序，看板会同步

> **这一停是硬性的。** 实测中模型曾在这里一口气把步骤生成、执行、报告全做完，用户完全没有机会改用例 —— 那样生成的步骤就是基于未经确认的用例，整轮结果作废。

### Step 3: 生成测试步骤

**整个项目所有用例一次全部生成。**

#### 关于「生成测试步骤」的话术（**由你编排**）

用户点「生成测试步骤」按钮后，**你要编排话术填进对话框**，内容必须包含**所有功能项下的所有用例**。

- 用户看到后**审阅**：有问题直接改，没问题点发送。
- 用户发送后你才开始生成步骤。
- 用户**可能会改这段话术**（比如去掉某几条用例）——**以用户实际发送的为准**，不要退回原样或强行生成被删掉的用例。

> 这与单元测试的 `prefillDraft` 是同一套机制：面板按钮触发、指令预填进对话框、用户审阅后发送。

#### 触发方式（不要自己开始）

1. 用户在**测试用例页审查完用例后**，点面板上的「生成测试步骤」按钮。
2. 宿主 `prepareStepGen` 负责执行准备（三件事）：
   - 新建一个步骤版本（**步骤页自己的编号**，例 `V0.0.1`）
   - 记 `sourceCaseVersion`（来源用例版本）
   - **冻结用例快照**到 `step-versions/<V>/cases.snapshot.json`
3. **你编排话术**：内容必须包含**所有功能项下的所有用例**，填进对话框。
4. **用户审阅**（有问题直接改）→ **点发送**。以实际发送内容为准。
5. 你这时才开始生成步骤。

**快照在生成步骤之前冻结**，不是等模型返回再存。这样即使生成期间用户改了用例，本次步骤版本对应的仍是点击那一刻的用例状态。

#### 生成什么

为**每条用例的每个步骤**生成：

- 步骤三元组：`action`（动作）/ `operation`（输入步骤）/ `expected`（预期结果）
- **对应的测试代码**（模型内部产物，界面不显示）

#### 步骤与测试函数一一映射

一个步骤 = 一个测试函数（例 `test_v0_0_1_it001_step1`）。这样才能单步执行。

**每个步骤的测试函数内部自带前置准备**（重复建环境），保证单独执行第 N 步也能跑。代价是慢，但可靠。

#### 写到哪

- 步骤进 `step-versions/<V>/steps.json` → 展示在**测试步骤页**
- 代码进 `integration/tests/`

**呈现原则（用户明确要求）**：用户只要步骤，不要测试代码的表现形式。面板、API、报告都不出现代码。

#### 生成完步骤之后：交给用户改

步骤会落到**测试步骤页**。用户可以：

- 主表操作列点「编辑」→ 增 / 删 / 改 / 查这条用例的步骤，可以调整顺序
- 改完保存，主表按改动显示

**所以步骤生成完也不是终点，不要自己接着执行。** 见 Step 4。

### Step 4: ★ 步骤人工审查

**生成完测试步骤后必须再次停下**，把主动权交给用户。这是流程的**第二个强制停顿点**。

用户此时会做：

1. **在测试步骤页审查并修改步骤**——编辑、增删、调顺序
2. **确认无误后点「一键执行」**（或某个步骤的「执行」图标做单步执行）

**你要做的**：

- 汇报步骤生成结果（见下），然后**停住**。
- **禁止自行执行测试。** 哪怕你觉得「步骤看起来没问题、可以直接跑」也不行。
- 用户改完后**重新读面板数据**再执行，不要用记忆里的旧步骤。

审查时汇报：

- 步骤版本号、来源于哪个用例版本（`sourceCaseVersion`）
- 步骤总数、覆盖的用例数、每条用例各几个步骤
- 哪些类型的步骤要走 CUA、哪些走 `run_tests.py`
- 提示用户：可以编辑任意步骤、调顺序，改完点「一键执行」

> **这一停也是硬性的。** 步骤是执行的依据；用户没看就执行，等于拿未确认的东西去跑出报告。

### Step 5: 执行测试

> **★★ 开跑前先做这一步（否则属于流程违规）**
>
> 判断被测系统的断言依据：**「界面上看到什么」还是「总线上出现什么帧/字段」**？
>
> | 判定 | 动作 |
> |---|---|
> | 多进程后端 / DDS / 消息总线 / 无界面 | **必须先读 [bus-backend/SKILL.md](bus-backend/SKILL.md)**，按它的阶段 1-7 准备工装与执行 |
> | 点按钮、读控件树 | 按 [desktop-e2e/SKILL.md](desktop-e2e/SKILL.md) 用 CUA |
> | 两者都有 | 两个都读；界面步与总线步的结论**互不影响** |
>
> 总线形态下**不要**直接用 `run_tests.py` 跑现成测试文件就算完 ——
> 需要先建工装三件套（观察者/仿真节点/注入器）与构建门，否则会退化成
> 「读代码推断总线行为」这种**产生假证据**的做法。

两种入口，**结果去处完全不同**：

| 触发方式 | 范围 | 结果落在哪 | 单条报告 | 产生报告版本 |
|---|---|---|---|---|
| **单步执行**（点某条**用例**的「执行」图标） | 一条用例的**单个步骤** | **测试步骤主表**该用例那一行下面的子表 +1 条，记录带 `source: "step"` | ✅ **必须生成**（落 `reports/<runId>/`，步骤页可看） | ❌ **不产生报告版本** |
| **一键执行** | 所有用例的所有步骤 | **测试报告页**，记录带 `source: "all"` | ✅ 逐条可看 | ✅ 新建报告版本 |

#### 单步执行（重点，与单元测试同一套流程）

```
① 用户在测试步骤页主表操作列点「执行」图标
        ↓
② 你编排执行指令并填进对话框（与单元测试单条执行完全相同的流程）
        ↓
③ 用户可自行修改话术 → 点发送
        ↓
④ 你按该用例的步骤逐步执行
        ↓
⑤ 「对话框里的结构」与单元测试单条执行保持一致
        ↓
⑥ 结果写入**测试步骤主表**该用例那一行下面的子表 → 多一条执行记录
        ↓
⑦ ★ **立即为这次单条执行生成 Word 报告**（见下「单条执行也要出报告」）
        ↓
⑧ 用户在这条执行记录的操作列点「查看报告」→ 开 tab 页展示（与单元测试相同）
        ↓
⑨ 导出：单条导出，流程与单元测试单条导出相同
        ↓
⑩ ❌ 不新建报告版本，不进测试报告页
```

**★ 执行记录必须标 `source`（决定进不进报告页）**

两部分页面靠这个字段分流，写错就会「单步执行的记录跑到报告页去」：

| source | 含义 | 出现在哪 |
|---|---|---|
| `"step"` | 单步执行（点了某条用例的「执行」） | **只在测试步骤页**的子表里 |
| `"all"` | 一键执行 | 测试报告页 + 步骤页子表 |

**每条执行记录都要写 `source`**，字段形如：

```json
{ "runId": "run_xxx", "at": "2026-11-19T16:36:43+08:00", "result": "pass", "durationMs": 1775, "source": "step" }
```

**没有 source 的旧记录会被当成单步执行**（不进报告页）—— 宁可少显示，也不要把单条记录混进报告页。

**★ 单条执行也要出报告（容易漏）**

单步执行的报告**不进测试报告页**，但这不代表不生成报告 —— **它必须生成，只是落在步骤页能看**。

| 项 | 要求 |
|---|---|
| 何时生成 | 执行结束、拿到结果后**立即生成**，不要等用户再点一次 |
| 放哪 | `integration/reports/<本次 runId>/` —— **用这次执行的 runId 建目录** |
| 内容 | **只取「4.1.1 测试结果总结」那一张表**，不按整本模板排版 |
| 文件名 | `集成测试报告-<caseId>-第<N>步-<版本>.docx` |
| 生成后 | 停下来把路径告诉用户，他要在子表点「查看报告」直接打开它 |

**报告主体必须列出整条用例的全部步骤**，本次没执行的标 `notRun`、`observed` 写「未执行（本次只执行第 N 步）」——不能只写执行的那一步。

**要点**：

- 话术**由你编排**，用户审阅后发送，**可能修改，以实际发送内容为准**。
- **只执行用户点的那一个步骤**，不要顺手把整条用例跑完。
- 单条执行结果的**查看报告 / 导出报告**与单元测试一致：开 tab 页查看、单个导出。

#### 一键执行

- 宿主 `prepareRun(scope: "all")` 冻结本轮所有步骤目标、导出用例快照、生成 runId，把命令填进输入框。
- **只需原样运行那条命令**，不要自己另拼 pytest / vitest / go test。
- `functional` 步骤由你直接调 CUA 执行（见下「两条执行通道」）。
- runner 边跑边写 `runs/<runId>/run.log`，结束时写 `result.json`。

**一键执行跑完后，你必须做两件事（都要做，不能只做一件）：**

1. **把执行记录挂到测试步骤主表每一行的子表里**
   每条用例主表都要加上这次的执行记录（执行结果、时间、耗时），用户在主表就能看到「这一条跑过了、结果如何」。
   **不能只把结果堆在报告页而让主表还是空的。**

2. **在测试报告页按功能项组织这批结果**
   - 按**功能项**分组
   - 每个功能项里，都能看到**该功能项下所有单条执行记录的报告**，可以**逐条查看 / 逐条导出**
   - 这里的单条报告与测试步骤页子表里的**是同一份东西**（都是 4.1.1 那张表），不要做成两套
   - 再上一层是**总体报告**按钮：出整个项目的一份测试报告，**按配置项测试报告模板整体排版**

**全部测试报告导出**与单元测试一致（多选 / 全选 / 导出已选）。

#### ★ 一键执行后的强制断言（**落盘后必须逐条核对，不通过不许进入 Step 6**）

执行记录写进 `exec-records.json` 之后，**立刻**按下面四条自查。任何一条不通过，
**先修数据再往下走**，不要让用户看到一份带着重复记录的报告。

| # | 不变量（公式级） | 怎么查 | 不通过怎么办 |
|---|---|---|---|
| 1 | **同一次 runId 在一条用例下只能有一条记录** | 对每条用例的 `records[]`，取 `runId` 去重后的数量，应与记录条数相等 | 去重：保留最后写入的那条 |
| 2 | **记录的 caseId 必须能在当版 cases.json 里找到** | 记录里的用例键 ⊆ `cases[].caseId` | 删掉挂不上用例的孤儿记录，并报出来 |
| 3 | **每条入选用例都必须有本轮记录** | 参与本轮执行的用例数 == 带本轮 `runId` 记录的用例数 | 缺的补一条 `result:"notRun"`，不许省略 |
| 4 | **记录里的 runId 必须能在 `runs/` 下找到目录** | 每条 `runId` 对应 `runs/<runId>/result.json` 存在 | 找不到就是证据缺失，明确报错，别写假记录 |

> **为什么必须有这一条**
>
> 用户实测遇到「一键执行后，每个步骤子表出现 2 条以上执行记录」。
> 根因是回写时**没有做幂等**：同一次 run 被写了多次（重跑、重复回写、或前后两次执行混在一起）。
> 子表按时间倒序展示，用户看到的就是「一次执行冒出好几条」，报告里的统计也跟着翻倍。
>
> 上面的表单就是防线：**写入前按 runId 去重，写入后逐条核对**。
> 这四条是**断言**，不是建议 —— 不通过就必须修，不许带着问题进报告阶段。

**★ 这四条也有脚本了，落盘后立刻跑：**

```
python <插件包>/assets/report/check_contract.py --root <项目>/.dsh/test-sessions/<SID>/integration --run <runId>
```

它除了上面四条，还会一起检查：`result.json` 是不是 `steps[]` 形态、
快照有没有冻结、报告版本是不是面板分配的、`steps.json` 有没有泄露函数名。
**必须 `结果：PASS` 才能进入 Step 6 生成报告。**

#### ★ 落盘后把完整报告摘要附在回复末尾

数据落盘并断言通过后，回复用户时**末尾附一段完整的结果摘要**，格式固定：

```
本轮执行摘要
- runId：<runId>
- 用例总数：N（通过 X / 未通过 Y / 未执行 Z）
- 记录条数：N（去重后）
- 不变量校验：4/4 通过
- 报告位置：<overallDocx 路径>
```

**为什么要求附这个**：用户不可能去翻 JSON 文件核对，摘要就是他唯一的验收依据。
没有这段摘要，等于让用户凭空相信「跑完了」。

#### 两条执行通道

| 类型 | 通道 | 证据来源 |
|---|---|---|
| `functional` 功能测试 | **CUA 桌面 MCP**（`mcp__cua__*`），按 [桌面端 E2E（CUA）](desktop-e2e/SKILL.md) | `model` |
| 其余 5 类 | `run_tests.py` 跑测试代码 | `runner+model` |

**CUA 由你自己直接调用，不需要用户再下一道指令。**

- **功能测试一定要用 CUA**——它就是用来**代替人手点击**的，不要退化成「读代码推断界面应该长什么样」。
- 单步执行、一键执行**都一样**：只要这一步需要操作真实界面，就自己调 `mcp__cua__*`。
- 一键执行时，`functional` 的步骤由你**逐步调用 CUA 执行**，不走 `run_tests.py`；其余 5 类走 runner。**两类在同一次执行里并存是正常的**，分别记录、分别标来源。
- **没有第三条通道。** 不要用 CUA 去假扮代码测试，也不要用 `run_tests.py` 去假扮界面操作。

#### 执行后必须回写观察

模型必须回写每步的 `observed`（**观察到的真实现象**），并按 [证据链三条硬校验](references/evidence-chain.md) 自查。回写的观察**不能直接当结论**，面板会校验（完整性 / 有据可依 / 不许超纲）。

### Step 6: 生成 Word 报告

**报告只消费「已经真实跑过的那次 run」**，永远指向具体那次执行，不随当前数据漂移。

## ★★ 集成测试报告与单元测试报告是两套东西，绝不能混用

**这是硬性边界，写代码/写脚本前先读这一节。**

| | 单元测试报告 | 集成测试报告 |
|---|---|---|
| 生成器 | `testReport/report-tool/bridge.py` + `builder.py` | `integrationReport/integration_report.py` |
| 入口函数 | `bridge.py` 的命令行 / `cmd.py` | `build_single_step()` / `build_full()` |
| 数据来源 | `result.json` 的 `tests[]`（逐测试函数） | `steps[]`（逐步骤）+ 快照用例 |
| 关键字段 | `scope`、`coverage`、`complexity`、`testFunc` | `stepVersion`、`caseVersion`、`caseCode`、`stages` |
| 模板 | 单元测试报告模板 + 覆盖率/圈复杂度章节 | 配置项测试报告模板（1 范围…附录 A/B） |
| 表格形态 | 按测试函数一行 | 单用例 16 行表 + 阶段分章 + 附录问题单 |

**绝对不要做的事**：

- ❌ 拿 `bridge.py` / `report-tool/` 生成集成报告
- ❌ 把集成数据（`steps[]`）喂给单元测试的 `builder.py`（字段对不上，直接取不到值）
- ❌ 在集成报告里写覆盖率、圈复杂度、MC/DC、测试函数名 —— 这些是单元测试的指标，集成测试没有
- ❌ 反过来把 `integration_report.py` 的逻辑套到单元测试数据上

**唯一的共用点**是「按 `runId` 定位报告目录 + 用系统关联程序打开 docx」这一条通用约定，
仅此而已。报告**内容**的每一个字都来自各自的生成器。

**为什么强调**（2026-11-20 用户明确要求）：两套报告的章节结构、表格形态、数据模型
完全不同。混用会直接产出错报告 —— 例如把集成数据喂给单元测试生成器，会得到一份
字段全空、章节对不上的 docx，而且**不会报错**，很难发现。

## ★ 报告必须调原型，不许自己写填表逻辑

**报告生成器**（`integration_report.py`）：**按插件包自身位置定位，不要写死绝对路径**。

查找顺序（与单元测试的 `run_tests.py` 同一套做法 —— 它用
`new URL('../assets/run_tests.py', import.meta.url)` 从包内解析，从不硬编码）：

1. `<插件包>/assets/integration_report.py` —— 随插件分发的首选位置
2. `<仓库根>/integrationReport/integration_report.py` —— 仓库内的开发态位置
3. 环境变量 `INTEGRATION_REPORT_SCRIPT` 指定的路径（特殊情况用）

**面板已经把真实路径回传给你**：`GET /data-panel/integration` 的响应里有
`reportScript` 字段，直接用它，别自己拼路径：

```python
# 优先用面板给的 reportScript；拿不到才按上面的顺序自己找
PROTOTYPE = PANEL_REPORT_SCRIPT or find_report_script()
```

> 为什么不写死：这条路径原来固定写成**某台机器上的绝对路径**，
> 别人 clone 到别的盘就失效 —— 而下面第 3 条又要求「缺失必须报错不许降级」，
> 于是换台机器报告直接生成不出来。**根因是路径写法，不是生成器本身。**

它对外只有两个函数，**报告一律从这里出**：

| 用途 | 函数 |
|---|---|
| 单条用例报告 | `build_single_step(template: Path, data: dict, out_path: Path)` |
| 整项目总体报告 | `build_full(template: Path, data: dict, out_path: Path)` |

**调用方式**（不要重新实现）：

```python
import importlib.util
from pathlib import Path

# PROTOTYPE 来自面板的 reportScript，或按上面 1/2/3 的顺序找到
spec = importlib.util.spec_from_file_location("ir", PROTOTYPE)
proto = importlib.util.module_from_spec(spec)
spec.loader.exec_module(proto)

proto.build_single_step(Path(TEMPLATE), data, Path(out_path))
```

### 三条铁律

1. **不许自己实现表格填充**。
   原型里包含了全部排版规范（不要章节号、测试类型映射、一页显示、人员默认值、问题单编号…）。
   自己写一套必然漏掉其中几条 —— 已实测踩过：单条报告套了整本模板、测试类型全写成「黑盒测试」。

2. **不许把原型复制一份改**。
   复制出去改 = 规范分叉，以后改了原型那份不跟随。**要改就改原型本身**。

3. **报告生成器缺失时明确报错，不许降级**。
   ```
   报告生成器缺失：<按上面 1/2/3 都找不到 integration_report.py>
   请确认该文件存在（它随仓库分发，见 integrationReport/README.md）；
   或用环境变量 INTEGRATION_REPORT_SCRIPT 指定路径。
   不要在缺生成器的情况下自己实现报告生成。
   ```
   不许静默退回「自己写个简单版」——那样出来的报告不符合规范，而且没人会发现。

### 写脚本是允许的，但只做「取数据 + 调原型」

### ★ 推荐做法：直接用 `bridge.py`，不要自己写转换脚本

仓库里已经有**数据转换层**，与单元测试的 `testReport/report-tool/bridge.py` 是同一个分工：

```powershell
cd <仓库根>\integrationReport
python bridge.py --session-root <会话>\integration `
                 --run-id <本次 runId> `
                 --project-code <项目缩写> `
                 --software-name "<软件名>" `
                 --software-version <版本> `
                 --report-version <面板分配的版本号>
```

它负责：读步骤/快照/执行结果 → 写 `report-plan.json` + `report-data.json` → 调生成器出 docx。

**两步分工（与单元测试一致）**：

```
steps.json + cases.snapshot.json + runs/<runId>/{result,observations}.json
        ↓  bridge.py                   ← 数据转换（本步可复核、可倒查）
report-plan.json + report-data.json
        ↓  integration_report.py       ← 填表排版
总体报告 + cases/*.docx
```

**为什么不要再自己写转换脚本**（这条踩过）：
转换逻辑散落在会话目录的临时脚本里，别人拉仓库后根本没有那份脚本；
而且每次重写都容易错字段（已踩过：`result.json` 的步骤号是 `stepNo` 不是 `no`，
写错会让 173 个步骤只匹配到 74 条证据、结论全变成「未执行」）。

自建脚本只在 `bridge.py` 不够用时才写，职责仍然只有「取数据 + 调生成器」：

```
读 steps.json / cases.snapshot.json / observations.json
        ↓
组装成原型要的 data 结构
        ↓
调 build_single_step / build_full
```

**填表、合并单元格、勾选框、分页控制全部由原型负责**，脚本里不该出现这些。

### ★ 用例标识：只认 `caseCode`，绝不用 `caseId` 兜底

报告里所有「测试用例标识」列**只能**出现规范形态：

```
GN-651-JYSG_DM_AUTH_LOGIN-1-T001.CTD
```

**不许**出现 `V0_0_1-IT-001` 这种内部主键 —— 它带版本前缀，肉眼看着就像版本号，
这正是「有的报告标识写得跟版本号一样、有的又对」的根因：

- 生成用例时产出了 `caseCode` → 报告对；
- 某批用例漏了 `caseCode`，旧代码拿 `caseId` 兜底 → 报告里就冒出个像版本号的串。

现在原型里的 `pick_case_code()` 已封死这条路：合法 `caseCode` → 用它；
没有/形状不合规 → **按规范现场生成**；连项目缩写都没有 → 写 `T001` 占位，
**无论如何都不会退回 `caseId`**。脚本侧只需保证每条用例都带 `caseCode`。

### 测试阶段：生成用例时就分成 3-4 个

用户明确要求（2026-11-20）：

- **生成用例时就把功能项分到 3-4 个测试阶段**，不要全塞进「第一阶段」。
- 阶段按**业务模块**划分（如：基础账号与商品 → 交易与支付 → 后台与消息），
  名称自定但要能看懂。
- 落进数据的字段：每个功能项带 `stage`，所属用例继承同一 `stage`。
- 报告侧因此会自然得到：
  - 3.1 总体评估 **每阶段一段**；
  - 3.1 分布统计表 **同阶段的「序号」「测试阶段」两列纵向合并**（一格代表该阶段的功能项数）；
  - **每阶段一组小计**（用例汇总 / 占总测试用例百分比%），表尾再来一行全项目总计；
  - 第 4 章起 **每阶段一章**（阶段 1 = 第 4 章，阶段 2 = 第 5 章…）。

### 表格排版：列宽固定铺满版心

原型已对所有数据表做 `tblLayout=fixed` + 逐列写死宽度（铺满 A4 版心 8306 缇），
并放开模板里 19 缇的过紧行距。**不要在脚本里再调列宽/字号**去凑观感 ——

| `ISSUE_TABLE_WIDTHS` | 3.1 软件问题分类统计（8 列） |
| `RECORD_TABLE_WIDTHS` | 3.1 测试结果记录单（6 列） |

| `APPENDIX_ISSUE_WIDTHS` / `APPENDIX_FIX_WIDTHS` | 附录 A / 附录 B |

### 附录 A / 附录 B：必须是表格，不许写成文字段落

用户明确要求（2026-11-20）：

- **附录 A 软件问题报告单**：每条问题**一张表**（模板「表x软件问题报告单」那张）。
  不许只写一行「问题编号 xxx：…」的文字。
- **附录 B 软件问题处理单**：每条问题**一张表**。
  **不许写「见上表，处理情况待补充」** —— 自己有表就自己填。
- 处理情况按**实际**填：本轮未修复就写「处理结果：未处理」+ 未处理原因，

数据侧要给的字段（可选，缺了原型会写合理默认值）：

```json
{
  "title": "问题标题", "desc": "问题现象描述", "level": "一般|严重|重大",
  "caseCode": "关联用例标识", "foundAt": "发现日期", "reportedAt": "报告日期",
  "suggestion": "更改建议",
  "handled": false, "fixReason": "未处理原因", "fixAction": "处理措施",
  "impact": "处理影响分析", "owner": "处理责任人", "fixDate": "处理日期"
}
```

### 模板里的 `xxx` 一律要换成真数据

模板中的 `xxx` 是**预留占位**，不是要照抄的内容。原型已覆盖：

| 位置 | 处理 |
|---|---|
| 3.1 总体评估 | 每阶段一段，填真实用例数/通过/未通过/问题数/起止日期 |
| 3.1 结尾段 | 软件名换真值；**代码注释率没有测量数据就整句不写**（不编百分比） |
| 3.2 充分性分析 | 用例总数 + 功能项覆盖 x/y；**不凭空写 100% 需求覆盖率** |
| 3.3 测试环境的影响 | 按 `meta.runEnv` 写实际环境，或按 `meta.envImpact` |
| 3.4 改进建议 | 模板固定文案，保留 |
| 附录 A/B | 表格逐格填真数据 |

#### 两种报告：取模板的不同范围（**这是核心区别**）

两类报告**用同一份配置项测试报告模板**（`配置项测试报告模板.docx`），区别只在**取模板的哪一部分**：

> **模板随仓库进库**（`integrationReport/配置项测试报告模板.docx`，90 KB），
> 克隆后直接可用 —— 与单元测试的 `testReport/templates/单元测试报告模板.docx` 一致。
> 查找顺序：命令行参数 → 环境变量 `INTEGRATION_REPORT_TEMPLATE` → 生成器同目录。
> **不要写死某个机器上的绝对路径**，也**不要**把模板放到桌面等仓库外位置。
>
> ⚠️ 单元测试模板（50 KB）和集成测试模板（90 KB）**不是同一个文件，不能互相替换**。

| | 单条执行报告 | 全部（一键执行）报告 |
|---|---|---|
| 取模板的哪部分 | **只取「4.1.1 测试结果总结」那一张表** | **按配置项测试模板整体编排**（1 范围 … 5 注释 + 附录） |
| 章节 | 不含完整章节结构 | 完整章节；`4.x` 按功能项循环 |
| 触发 | 步骤页某条执行记录点「查看报告」/ 导出 | 报告页，一键执行后生成 |
| 查看 | 开 tab 页（与单元测试一致） | 测试报告页，按功能项分组 |
| 导出 | **单个导出**（与单元测试单条导出一致） | 全部导出（与单元测试一致） |

> 一句话记法：**单条 = 第 4.1.1 节下面那一张表；全部 = 整本配置项测试模板。**

#### 单条报告 vs 总体报告：**存放位置与生成器函数都不同**

| | 单条报告（每条用例一份） | 总体报告（整项目一份） |
|---|---|---|
| 生成器函数 | **`build_single_step()`** | **`build_full()`** |
| 套多少模板 | **只取 4.1.1 那一张表** | 整本（1 范围 … 5 注释 + 附录） |
| 存放 | `reports/<runId>/cases/` | `reports/<runId>/`（与 cases/ 平级） |
| 文件名 | `集成测试报告-<caseId>-全步骤-<版本>.docx` | `集成测试报告-<项目名>-整项目-<版本>.docx` |
| 数量 | 60 条用例 → **60 份** | **1 份** |

**最容易犯的错**：用 `build_full()` 给每条用例生成单条报告 —— 结果是 60 份 70KB 的整本报告，
而不是只含一张表的短报告。**单条报告必须用 `build_single_step()`。**

#### 单条报告：一张表，不要章节号

单条报告**不生成完整报告文档**，只保留模板里 4.1.1「测试结果总结」那张表并填好。

**★ 不要章节标题和表题**（用户明确要求，已踩过坑）：

- ❌ 不要 `4.1 用户注册与登录` 这类功能项章节号
- ❌ 不要 `4.1.1 测试结果总结`
- ❌ 不要 `表1 标识 V0_0_1-IT-002 第 1-3 步` 这类表题文字

**单条报告 = 标题 + 一张填好的表**，别的都不要。章节号是整本项目报告才有的东西。

**★ 整表落在一页**：给每一行加 `cantSplit`（行内不断页）+ 除末行外加 `keepNext`（与下行同页），避免一张表被切成两页。

**★ 测试类型 vs 测试方法（两个不同的格，别写成一个）**：

| 格 | 填什么 |
|---|---|
| **测试类型** | **按用例自身的 `type`**：功能测试 / 接口测试 / 边界测试 / 性能测试 / 安全性测试 / 余量测试 |
| **测试方法** | 固定写「黑盒测试」 |

**常见错误**：两格都写「黑盒测试」。黑盒测试是**方法**，不是**类型** —— 接口用例的类型必须是「接口测试」。

**★ 人员与问题单的暂定值**：

| 字段 | 现在写什么 |
|---|---|
| 设计者 / 校对者 / 测试人员 | **`admin`**（还没有规范，暂定） |
| 软件问题单编号 | **`无`** |

> 这两条是用户明确交代的「先这样」，等有规范了再改。

**填这张表时，仍要展示整条用例的全部步骤**，只有本次执行的步骤有结果：

```
人员三字段：现在暂定都写 admin
功能项：{ code, name }
用例：{
  caseId, title, type, requirement, description, precondition, executedAt, outcome,
  steps: [
    { no:1, action, operation, expected, observed, outcome },
    { no:2, action, operation, expected, observed, outcome },   ← 本次执行的这一步
    { no:3, ..., observed: "未执行（本次只执行第 2 步）", outcome: "notRun" },
    { no:4, ..., observed: "未执行（本次只执行第 2 步）", outcome: "notRun" }
  ]
}
```

**硬性要求**：

1. **不要只写执行的那一步**。整条用例的步骤都要列出来，未执行的写 `notRun` 并注明原因。
2. 未执行步骤的 `observed` 写「未执行（本次只执行第 N 步）」，不要留空，也不要写「通过」。
3. `outcome` 取值：`passed` / `failed` / `error` / `notRun`（未执行）。
4. 报告里**不出现测试代码、测试函数名、codeRef**。
5. 单用例表是模板表4（**5 列 16 行**），步骤行按实际步骤数**自动增删**（4 步→17 行，2 步→15 行）。

#### 全部报告：按阶段分章，套整本配置项测试模板

一键执行的报告**走完整模板结构**，并且**按测试阶段分章**。这块规则最多，逐条照做。

##### ① 章节骨架

```
1.范围  → 1.1标识 / 1.2系统概述(表1 软件信息表) / 1.3文档概述
2.引用文档
3.测试结果概述
    3.1 总体评估（★ 按阶段数展开段落，见下）
    3.2 充分性分析 / 3.3 环境影响 / 3.4 改进建议
4.<阶段1名>详细测试结果     ← 每个阶段一章
    N.1 <功能点名称>                ← 每个功能项一节
        N.1.1 测试结果总结          ← 该功能点下**所有用例表**连续列在这里
            表1 标识<用例标识>
            表2 标识<用例标识>
    N.2 <下一个功能点名称>
        N.2.1 测试结果总结
            …
    N.n   遇到的问题                ← 所有功能点之后，n = 功能点数 + 1
    N.n+1 与测试用例/规程的不一致
    N.n+2 回归测试                  ← 章内最后一节
        N.n+2.1 <功能点名>          ← ★ 下面**直接接表**，没有 .1 那层测试结果总结
5.<阶段2名>详细测试结果     ← 结构与第 4 章完全一样
…
注释
附录A 软件问题报告单
附录B 软件问题处理单
```

**章号规则**：第 1 个阶段是 `4` 章，第 2 个阶段是 `5` 章，依此类推（`阶段序号 + 3`）。

##### ② 3.1 总体评估：**按阶段数展开段落**

模板里那块是**制式段**，写着「总共有 x 个这样的段」。

- **有几个测试阶段，就复制几段**（2 个阶段 → 2 段）
- 每段填该阶段的数据：用例总数 / 执行数 / 通过数 / 未通过数 / 问题数 / 阶段名
- **最后一段固定**：「经本次配置项测试验证，…软件实现了…」只替换软件名

##### ③ 表2 分布统计（功能项 × 7 类）

| 列 | 规则 |
|---|---|
| 需求功能项 | 生成用例时归类的**功能项名称** |
| **测试功能** | ⚠️ **写成「功能测试」**（模板原文字是错的） |
| 7 类各列 | **没有就写 `0`，不要空着** |
| 测试阶段 | **不能空**，填该功能项所属阶段 |

##### ④ 表3 问题分类统计

- 「合计问题数」**没有就写 `0`**
- 「测试问题归零解决情况」**没有就写 `无`**

##### ⑤ 表4 测试结果记录单

| 列 | 填什么 |
|---|---|
| 测试阶段 | 该用例所属阶段，**不能空** |
| 功能点名称 | 生成用例时归类的功能项 |
| **详细需求追踪条目** | 用例标识去掉 `-N-Tnnn.CTD` 尾部 |
| **用例标识** | 规范标识（见下「用例标识规范」） |
| 结论 | 通过 / 未通过 / 未执行 / 未确认 |

##### ⑥ 用例标识规范（**必守**）

格式：

```
GN-651-JYSG_SRS_UI_TESTING-1-T001.CTD
│   │   │    │   │          │ └─ 顺序号 T001、T002…
│   │   │    │   │          └─── 1=正常用例  2=专门测异常情况的用例
│   │   │    │   └────────────── 需求文档章节英文名；无需求文档用功能点英文名
│   │   │    └────────────────── SRS=按需求规则文档 / DM=按代码归纳
│   │   └─────────────────────── 项目缩写（如 肌颜时光 → JYSG）
│   └─────────────────────────── 固定 651，不变
└─────────────────────────────── 测试类型缩写
```

**测试类型缩写对照**：

| 类型 | 缩写 |
|---|---|
| 功能测试 | `GN` |
| 接口测试 | `JK` |
| 安全性测试 | `AQ` |
| 性能测试 | `XN` |
| 边界测试 | `BJ` |
| 强度测试 | `QD` |
| 余量测试 | `YL` |

**最后一段 `.CTD` 固定不变**。

**详细需求追踪条目** = 用例标识去掉 `-1-T001.CTD`：

```
用例标识：          JK-651-JYSG_DM_API_TESTING-2-T002.CTD
详细需求追踪条目：  JK-651-JYSG_DM_API_TESTING
```

**生成时机**：生成用例时**每条用例当场生成**，存进 `caseCode` 字段。
内部主键 `caseId` 保持不变（面板、执行记录靠它关联），`caseCode` 只用于报告和界面展示。

##### ⑦ 测试阶段从哪来

| 情形 | 怎么定阶段 |
|---|---|
| **有需求规则文档** | 文档里通常已划分阶段（如「第一阶段」「sprint1」），按文档 |
| **无需求规则文档** | 读代码自己划分（按迭代痕迹、版本提交、模块演进） |
| 用户明确指定 | 按用户说的 |

**一个阶段可以包含多个功能项**（如 sprint1 含「用户注册与登录」「商品浏览」）。

##### ⑧ 数据来源与结论标注

**只认快照**：`cases.snapshot.json`（生成步骤时冻结的用例）与 `runs/<runId>/snapshot/`，**不读当前用例版本**。这样即使用例后来被改得面目全非，报告依然可复现。

- 结论粒度是**一个步骤一条**（不是一条用例一条）
- **必须标注结论来源**：`runner+model`（5 类，代码真跑过 + 模型补充观察）与 `model`（功能测试，只有模型记录），两者视觉上要能区分，不混成一类可信度
- 报告里**不出现测试代码、测试函数名、codeRef**

## 数据模型

> **★ 契约逐字声明（写文件前先读这一段）**
>
> 下面每个 JSON 实例就是面板的**接口契约**。面板按这些字段名直接读取，
> 字段名对不上，面板就读不到 —— 界面上表现为「数据是空的」或「展开一行全展开了」。
>
> 因此：
> 1. **逐字段照抄**，禁止自拟字段名、禁止改数据形态（数组不能写成对象、字符串不能写成数组）。
> 2. 需要额外信息就**新增字段**，不要改动已有字段的含义。
> 3. 标注「面板补」的字段**不用你写**，面板会自己补；写错了也不影响。
> 4. 标注「必填」的字段**必须写**，缺了面板会当成脏数据跳过。

### 功能项

```json
{
  "id": "ft_xxx",
  "code": "F-001",
  "name": "<功能项名称>",
  "description": "<这个功能项覆盖什么行为>",
  "source": "requirement | skill | code-derived"
}
```

> **字段说明**
>
> - `id`（**必填**）：功能项的唯一标识，用例的 `featureId` 指向它。**面板按它对应用例归属**，缺了用例就挂不到功能项上。格式建议 `ft_` + 数字/短名。
> - `code`（必填）：给人看的编号，报告「测试需求追踪」列用它。
> - `name`（必填）：面板显示的功能项名称，同一版本内**不能重复**。
> - `stage`（**必填，且用例必须继承**）：报告**完全按它分章**。生成用例时没写，
>   整份报告只能退化成「全是第一阶段」，**事后无法补救**。全项目 3-4 个阶段为宜。
>   > 实测教训：功能项写了 `stage`、用例一条都没继承（74/74 缺失），校验器以前也没查。
>   > 现在 `stage` 是 FAIL 级检查，两处都会拦。

### 用例

```json
{
  "id": "it_xxx",
  "caseId": "V0_0_1-IT-001",
  "featureId": "ft_xxx",
  "title": "<这条用例验证什么>",
  "type": "functional",
  "description": "说明前置状态、操作、具体输入、验证目标",
  "precondition": "<执行前需要满足的状态>",
  "expectedResult": "<预期的最终结果>",
  "steps": []
}
```

> **字段说明**
>
> - `id`（写不写都行，**面板会补**）：面板内部认行用的键 —— 展开子表、勾选、列表 key 都靠它。
>   文件里没写时面板自动用 `caseId` 兜底，所以**不会出问题**；写了就用你写的。
>   > 历史坑：这里以前有 `id` 但没写用途，文件里又实际不写，导致面板拿到的 `id` 是空的，
>   > 「点一行展开，所有行一起展开」。面板现在已用 `caseId` 兜底修好，但规范里必须说清它干什么用。
> - `caseId`（**必填**）：用例标识，形如 `V0_0_1-IT-001`，**同名版本内唯一**。面板、步骤、执行记录全靠它关联。
> - `featureId`（必填）：指向功能项的 `id`，决定这条用例归到哪个功能项下。
> - `title` / `type` / `description` / `precondition` / `expectedResult`（必填）：面板列表与报告直接取这些字段显示。
> - `steps`：留空数组。步骤在 Step 3 单独生成、单独存版本，**不要写在这里**。

### 步骤（执行原子）

单条步骤长这样：

```json
{
  "no": 1,
  "action": "<这一步做什么>",
  "operation": "<具体怎么操作：输入什么、点哪里>",
  "expected": "<可观察的预期结果>",
  "target": "test_v0_0_1_it001_step1"
}
```

#### ★ `steps.json` 的顶层结构：**必须按用例分组**

```json
{
  "stepVersion": "V0.0.1",
  "sourceCaseVersion": "V0.0.1",
  "generatedAt": "2026-11-20T10:00:00+08:00",
  "channelLegend": { "cua": "界面自动化", "runner": "测试代码" },
  "cases": [
    {
      "id": "it_1",
      "caseId": "V0_0_1-IT-001",
      "caseCode": "GN-651-JYSG_DM_AUTH-1-T001.CTD",
      "featureId": "ft_001",
      "featureName": "用户注册与登录",
      "title": "手机号验证码登录",
      "type": "functional",
      "createdAt": "2026-11-20T10:00:00+08:00",
      "steps": [ { "no": 1, "action": "...", "operation": "...", "expected": "...", "target": "...", "channel": "cua" } ],
      "records": []
    }
  ]
}
```

> **★★ 最常见的致命错：把 steps.json 写成扁平数组。**
>
> 错（面板读不到，**测试步骤页整片空白**）：
> ```json
> [ { "caseId": "V0_0_1-IT-001", "no": 1, ... }, { "caseId": "V0_0_1-IT-001", "no": 2, ... } ]
> ```
> 也错：`{ "stepVersion": "...", "steps": [ {...} ] }`
>
> 对：`{ "cases": [ { "caseId": "...", "steps": [ {...} ] } ] }` —— **每条用例挂自己的 steps**。
>
> 用户 2026-11-23 实测踩到：模型写成扁平数组，磁盘上明明有步骤，界面什么都不显示。
> 面板已加兼容兜底（会按 caseId 自己分组），但**契约仍是分组式**，校验器会直接 FAIL。

### 执行记录（**挂在测试步骤主表某一行下面，用例级**）

子表里的一条记录（与面板 `record()` 一致，**只这四个字段**）：

```json
{
  "runId": "run_xxx",
  "at": "2026-11-19T10:24:00",
  "result": "pass | fail | error",
  "durationMs": 4820
}
```

**逐步骤的详细结果不存这里**，在 `runs/<runId>/result.json` 里；观察文字在 `runs/<runId>/observations.json` 里：

```json
{
  "runId": "run_xxx",
  "caseId": "V0_0_1-IT-001",
  "stepNo": 1,
  "target": "test_v0_0_1_it001_step1",
  "outcome": "passed | failed | error | skipped | notRun | unknown",
  "durationMs": 123,
  "startedAt": "2026-11-19T09:00:00+08:00",
  "observed": "页面加载完成，标题「无线蓝牙耳机」，价格 ¥299",
  "evidence": ["runs/<runId>/shots/step-1.png"],
  "evidenceSource": "runner+model | model"
}
```

**`outcome` 只认硬证据**：`runner+model` 来自 `result.json` 的逐条结果；`model` 来自 CUA 实际调用返回。找不到证据就标 `unknown`/`未确认`，**绝不用整体状态推断通过**。

> ★ 注意 `outcome` 的合法值是 **`passed` / `failed` / `error` / `notRun` / `unconfirmed`**（来自 `bridge.py` 的 `OUTCOME_CONCLUSION`）。
> 不是 `pass`，也不是 `skipped`。写错报告会取不到结论。

### `runner.json`（跑测试代码的 5 类必须写）

```json
{
  "preset": "pytest",
  "testFile": "root:integration/tests/test_integration_api.py",
  "mode": "batch"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `preset` | 是（三选一） | `pytest` / `node-test` / `gtest-batch` 等，见单元测试 runner 的预设清单 |
| `testFile` | 是（与 `command` 二选一） | 测试文件路径；`root:` 前缀表示相对项目根 |
| `command` | 是（与 `testFile` 二选一） | 完全自定义命令，数组形态 |
| `mode` | 否 | `batch`（整批跑）/ `per-case`（逐条跑） |

> **`runner.json` 放在 `<integration>/runner.json`（集成根下）**，不是放进版本目录。
> 历史上这里只写了「格式与单元测试完全一致」，执行者只能猜 —— 结果整份没写，
> 跑测试代码的 5 类直接没法执行。

### `runs/<runId>/result.json`（**报告管线的真实输入，最容易写错**）

```json
{
  "runId": "run_20261120_1852_all",
  "stepVersion": "V0_0_1",
  "caseVersion": "V0_0_1",
  "startedAt": "2026-11-20T18:52:00+08:00",
  "steps": [
    {
      "caseId": "V0_0_1-IT-001",
      "stepNo": 1,
      "target": "test_v0_0_1_it001_step1",
      "channel": "cua",
      "outcome": "passed",
      "durationMs": 1200,
      "observed": "登录页渲染完成",
      "reason": ""
    }
  ]
}
```

**★★ 必须是 `steps[]`，不能是 `tests[]`。**

| | runner 原生输出 | `bridge.py` 需要的 |
|---|---|---|
| 顶层键 | `tests[]`（逐测试函数） | **`steps[]`（逐步骤）** |
| 每项键 | `name` / `status` / `duration` | `caseId` / `stepNo` / `channel` / `outcome` |

> **这是本次审计发现的最高价值问题。** `bridge.py` 的 `load_execution()` 只读 `result.json`
> 的 `steps[]`；而 pytest / vitest 的原生报告是 `tests[]`。Skill 两头都没写清楚，
> 执行者只能自己「打派生视图补丁」才跑通报告 —— 那既不可复现，也没人知道对不对。
>
> **正确做法**：runner 跑完后，由你**按上面的形态重新写一份 `result.json`**，
> 逐步骤映射（一个测试函数对应一个 `stepNo`）。不要指望 runner 直接产出这个形态。
>
> `channel` 只能是 `runner` 或 `cua`；`outcome` 见上一条的合法值。

## 存储结构

```
<项目>/.dsh/test-sessions/<sessionId>/integration/
  case-versions/                 # 用例页
    index.json                   # { versions: [{ name, at, status }], activeVersion }
    V0_0_1/ features.json  cases.json
  step-versions/                 # 步骤页（独立编号）
    index.json                   # { versions: [{ name, sourceCaseVersion }], activeVersion }
    V0_0_1/ steps.json  cases.snapshot.json   # ★ 快照冻结
    V0_0_1/ exec-records.json    # ★ 该版本下每条用例的执行记录（多次一键执行累积）
  report-versions/               # 报告页（独立编号）
    index.json                   # { versions: [{ name, sourceStepVersion, runId }], activeVersion }
    V0_0_1/ report.json
  tests/                         # 测试代码（内部产物，界面不展示）
  runs/<runId>/
    request.json                 # 冻结本次要跑哪些步骤
    snapshot/                    # 本次执行的快照（steps + cases + 代码）
    result.json                  # runner 写的硬证据
    observations.json            # 模型回写的观察
    run.log
  reports/<runId>/ *.docx
```

**执行记录挂在哪（关键）**：

- 执行记录挂在**步骤版本**下，**按用例分组**，一条用例一份数组。这与面板现状一致（`records[]` 挂在用例上，不挂单个步骤上）。
- **一键执行多少次，该数组就追加多少条**；步骤版本本身**不会因此增加**。
- 数组按时间**倒序**存（最新在最前），面板取 `records[0]` 显示「最新一次结果」。

**一条执行记录只存四个字段**（与面板 `record()` 一致）：

```json
{
  "V0.0.1": {
    "V0_0_1-IT-001": [
      { "runId": "run_…", "at": "2026-11-19T10:24:00", "result": "pass",  "durationMs": 4820 },
      { "runId": "run_…", "at": "2026-11-19T09:02:00", "result": "fail",  "durationMs": 6310 }
    ],
    "V0_0_1-IT-002": [ … ]
  }
}
```

| 字段 | 含义 |
|---|---|
| `runId` | 对应 `runs/<runId>/`，**详细结果和 `observed` 都在那里** |
| `at` | 测试时间 |
| `result` | `pass` / `fail` / `error` |
| `durationMs` | 耗时 |

**执行记录里不存 `observed`、不存逐步骤结果。** 那些都在 `runs/<runId>/result.json` 与 `observations.json` 里，报告或查看时按 `runId` 去读。这样执行 10 次也只多 10 条四字段小记录，不会把观察文字复制 10 份。

**为什么三套都要 `index.json`**：每个页面自己维护版本清单和「当前查看哪个版本」。切版本时只读对应目录，不用过滤，也不会互相污染。

**三个冻结点**（理由与单元测试一致：报告只能反映「当时跑的那一份」）：

| 冻结点 | 冻结什么 | 存在哪 |
|---|---|---|
| 生成步骤时 | 当时的用例与功能项 | `step-versions/<V>/cases.snapshot.json` |
| 每次执行时 | 本次要跑的步骤 + 用例 + 代码 | `runs/<runId>/snapshot/` |
| 生成报告时 | 只消费该 run 的快照 | `report-versions/<V>/report.json` 记 `runId` |

## 面板 API

地址取 `$env:DSH_WEB_URL`（当前 DSH 页面地址）。集成测试用**独立路径**：

```
$env:DSH_WEB_URL/data-panel/integration
```

**不要复用单元测试的 `/data-panel/api`。** 原因（已核实，不是偏好）：

- 后端 `TEST_TYPES` 硬校验 5 类，集成测试的 `stress` / `security` / `margin` 会被直接拒（400）。
- 单元测试 store 没有「版本 / 功能项 / 步骤」这三层结构。
- 共用会污染单元测试的用例数据与行为。

所有接口**必须**带当前会话 ID。`sessionId` 缺失或为空 → 返回 400，不会静默写到其他位置。

> ✅ **当前实现状态（2026-11-20 已实现，不要再按旧说法汇报）**
>
> 集成测试数据层**已经实现**。面板直接读取会话目录下的 JSON 文件，
> 数据只写文件，**文件格式就是面板的接口契约**。
>
> 因此现阶段：
> 1. 用例 / 步骤 / 报告数据**写文件**即可，面板刷新就能看到。
> 2. **不要再说「面板 API 未实现」「数据未同步到面板」**——那是阶段 1 之前的旧状态。
> 3. 写文件必须严格按「数据模型」一节的字段，见下一节开头的契约声明。
> 4. 面板自己会读所有版本的内容，**不需要**为了「让用户看到新版本」而让用户回对话切版本。

约定接口：

```
GET  /data-panel/integration?sessionId=<SID>&kind=case|step|report
POST /data-panel/integration { sessionId, kind, op, ... }
     kind=case   op=createVersion / saveVersion / setActive
     kind=step   op=createVersion / saveVersion / setActive
     kind=report op=createVersion / saveVersion / setActive
```

**写文件是主路径，接口是面板自己用的**。你按上面的存储结构直接写 JSON 文件，
面板刷新就能读到；不必绕道调接口。

## 重要规则

- **禁止未经用户确认就执行测试**
- **禁止跳过两处人工审查**：Step 2（用例人工审查）和 Step 4（步骤人工审查），两处都必须停
- **用户全程可改数据**：用例、步骤都能被用户在面板上增删改查、调顺序。你交付的是**初稿**，不是成品。**每次继续之前重新读面板当前数据**，不要用自己生成的记忆往下走。
- **用户发送前可能修改话术**：以用户**实际发送**的内容为准，不要退回原样、不要强行生成被删掉的用例。
- **不要绕过面板自己开始生成或执行**：这些动作都要先由面板按钮触发，再由**你编排话术**、用户审阅发送。不要抢在用户点按钮之前自行开工。
- **三个页面版本各自独立编号**，不要写成「一个版本包含全部」
- **版本数 = 动作次数**：生成用例→用例页+1；生成步骤→步骤页+1；一键执行→**报告页**+1。**一键执行不会让步骤页多版本**，只会给每条用例的子表**追加一条执行记录**
- **代码是内部产物**：界面、面板 API、报告都只出现步骤，不出现测试函数名 / 代码片段 / codeRef
- **生成步骤时冻结用例快照；执行只认快照**，不读当前用例版本
- **一个步骤 = 一个测试函数**，步骤函数自带前置准备
- **强度测试本轮不生成**
- **单步执行的结果留在步骤页**，可查看/导出单条报告，但**不进报告页、不产生报告版本**
- **执行记录必须带 `source`**：单步执行 `"step"`（只在步骤页）、一键执行 `"all"`（进报告页）。report页只显示 source="all" 的记录
- **单步执行也必须生成单条报告**（`integration/reports/<runId>/`，只取 4.1.1 那张表）；「不进报告页」不等于「不出报告」
- **子表挂在测试步骤主表的每一行下面**：主表一行 = 一条用例，子表 = 这条用例的执行记录；一条记录一次执行（单步算一条、一键也算一条），**混在同一个子表里，靠时间区分**
- **执行记录只存 `runId` / `at` / `result` / `durationMs` 四个字段**，不存 `observed`、不存逐步骤明细（那些在 `runs/<runId>/` 里）
- **报告必须调生成器** `integrationReport/integration_report.py`（`build_single_step` / `build_full`），**不许自己写填表逻辑、不许复制生成器改、生成器缺失要报错**。路径按插件包自身位置解析（见上文），**不要写死绝对路径**
- **单条报告只取 4.1.1「测试结果总结」那一张表**，用 `build_single_step()`，落 `reports/<runId>/cases/`（60 条用例 = 60 份）
- **总体报告按配置项测试模板整体编排**，用 `build_full()`，落 `reports/<runId>/`（整项目只有 1 份）
- **单条报告要列出整条用例的全部步骤**，未执行的标 `notRun` 并注明「未执行（本次只执行第 N 步）」
- **只有两条执行通道**：CUA（`functional`）、`run_tests.py`（其余 5 类）。不要互相假扮
- **模型回写的观察必须过三条硬校验**，找不到证据标「未确认」，不冒充 runner 证据
- **编译错误和依赖缺失视为执行失败，不是通过**
- **用户界面文本用中文，代码用英文**
- **进度必须用 `todo_write`**：开工先写 6 步（两个审查各占一条待办），每完成一步立即更新
- **不要静默跳过功能项**：没纳入的写进覆盖清单并说明理由，不能只在对话里含糊带过
