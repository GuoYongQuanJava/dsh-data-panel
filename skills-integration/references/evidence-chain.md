# 证据链：三条硬校验

Step 5 执行后回写观察时阅读。**模型回写的观察不能直接当结论**，面板侧必须校验。

## 为什么需要这一层

集成测试有两种证据来源，可信度不同：

| 来源 | 内容 | 可信度 |
|---|---|---|
| `runner` | `result.json` 里逐条的 `outcome`、耗时、退出码；UIA 脚本读到的控件属性 | 硬证据，可复现 |
| `model` | 模型回写的 `observed`（肉眼看到什么） | 辅助证据，可读性好但可能编 |

**模型很容易把「我觉得应该通过」写成「观察到的现象」**，所以必须有一条机器可校验的边界。

## 三条硬校验

| # | 校验 | 规则 | 不通过时 |
|---|---|---|---|
| 1 | **完整性** | 回写的步骤号集合 == `request.json` 冻结的 targets 集合 | 缺哪步 → 标 `unconfirmed` |
| 2 | **有据可依** | `outcome: passed` 时 `observed` 不能为空 | 降级为 `unconfirmed` |
| 3 | **不许超纲** | 只能写 targets 里有的步骤号 | 多出的**丢弃** |

**顺序**：先校验 3（丢弃超纲），再校验 1（找缺失），最后校验 2（passed 必须有观察）。

### 校验 1：完整性

```
request.json 的 targets = [step 1, step 2, step 3]
observations 里的步骤号 = [1, 3]
→ step 2 标 unconfirmed，不能默认它通过
```

**不能用「整体通过」推断单步通过。** 整体状态是 5/6 也好、100% 也好，逐条结论只看逐条证据。

### 校验 2：有据可依

`outcome: passed` 但没有 `observed` 的步骤，**降级为 `unconfirmed`**。

**为什么**：说「通过了」却说不清看到了什么，等于没有证据。尤其在界面断言里，这是唯一能防编造的东西。

**注意**：`observed` 写「页面正常」「符合预期」这类空话，形式上过了校验，实质上没有证据价值。要写**可复现的具体现象**：

```
❌ "页面正常显示"
✅ "页面标题栏显示「无线蓝牙耳机」，价格区显示 ¥299，购物车角标为 1"
```

### 校验 3：不许超纲

回写里出现了 `request.json` 没冻结的步骤号 → **直接丢弃**。

**为什么**：防止模型把「上次跑的」「别的用例的」「自己想象的」步骤结果混进本次记录。

## 报告里必须标明来源

| 来源标记 | 适用 | 含义 |
|---|---|---|
| `runner+model` | **默认**。runner 跑测试代码、`cmd` 命令步、`uia` 界面断言 | 硬证据（可复现）+ 模型补充观察 |
| `model` | 仅模型肉眼补充的描述性观察，或历史数据遗留 | 只有模型记录，**没有可复现证据** |

**两种来源在报告里视觉上要能区分，不能混成一类可信度。** 读报告的人必须一眼看出「这条结论是代码/脚本跑出来的，还是模型肉眼记下来的」。

> **`uia` 步骤默认标 `runner+model`**：UIA 脚本读到的控件属性可复现、可重跑，属于硬证据。
> 不要因为它「看着像界面」就降级成 `model`。

## `outcome` 的取值规则

| 值 | 什么时候 | 证据要求 |
|---|---|---|
| `passed` | 断言成立 | runner 逐条结果，或 UIA 读到的控件属性满足断言 |
| `failed` | 断言不成立 | 必须有失败原因原文 |
| `error` | 执行本身出错（崩溃、超时、环境缺依赖） | 必须有错误原文 |
| `skipped` | 明确跳过 | 写明跳过原因 |
| `notRun` | 本次没有执行这一步（单步执行时其余步骤） | `observed` 写「未执行（本次只执行第 N 步）」 |
| `unknown` | 找不到证据 | 不能猜 |

**编译错误、依赖缺失、环境问题视为执行失败，不是通过。**

**`notRun` 不是失败**：单步执行时，一条用例里没跑到的步骤都是 `notRun`。它表示「本次没验证」，不能算通过，也不能算缺陷。

## 界面断言（`channel: uia`）怎么取证

界面步的结论来自 UIA 读到的控件属性，**不是截图**：

1. **每个断言都读真实控件属性**（`AutomationId` / `Name` / `Current.Value` / `IsEnabled` / `ToggleState`），不要靠截图「看着像」。
2. `observed` 写**读到的真实控件文本/属性值**，不是形容词。
3. 需要视觉证据时保留截图路径到 `evidence[]`（**只作辅助，不能替代属性断言**）。
4. **属性断言不成立就是 `failed`**，不要因为「界面看起来差不多」改成通过。
5. **读不到控件**（自绘控件、非标准布局、窗口最小化）→ 记 `blocked` 并写明原因，**不算通过也不造假**。

详细操作见 [界面断言（UIA）](../desktop-uia/SKILL.md)。

## 回写 `observed` 的正确姿势

```json
{
  "caseId": "V0_0_1-IT-001",
  "stepNo": 1,
  "target": "test_v0_0_1_it001_step1",
  "outcome": "passed",
  "observed": "窗口标题「购物车 - 我的商城」；表格第 1 行 Name=无线蓝牙耳机，Qty=1，Subtotal=¥299.00",
  "evidence": ["runs/run_20261119_0900/shots/step-1.png"],
  "evidenceSource": "runner+model"
}
```

**要点**：
- 写**具体值**，不写判断词。
- 一条观察只对应一个步骤号。
- 不复制预期结果充当观察——那是造假。**实际值和预期值恰好相同也要来自真实读取。**

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 漏写某步的观察 | 该步无法判定 | 缺就标 `unconfirmed`，不要补编 |
| `passed` 但 `observed` 为空 | 无证据的通过 | 降级为 `unconfirmed` |
| 写了没冻结的步骤号 | 数据污染 | 丢弃超纲项 |
| 用「整体通过率」推断单步 | 结论失真 | 只看逐条证据 |
| 把预期结果抄成观察结果 | 证据造假 | 观察必须来自真实读取/返回 |
| 界面步明明读了控件属性却标 `model` | 无谓降低可信度 | 脚本读到就标 `runner+model` |
| 肉眼观察硬标 `runner+model` | 抬高可信度 | 没有可复现证据只能标 `model` |
| 编译失败却记成 `error` 之外的通过 | 掩盖失败 | 执行失败就是失败 |
