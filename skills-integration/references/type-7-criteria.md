# 7 类判定标准

Step 2 生成用例时阅读。**枚举固定，不能自造类型。**

```js
functional   / 功能测试
performance  / 性能测试
boundary     / 边界测试
api          / 接口测试
stress       / 强度测试   ← 本轮不测，禁止生成
security     / 安全性测试
margin       / 余量测试
```

## 先分清最容易混的三组

| 组合 | 区别 | 判定动作 |
|---|---|---|
| `boundary` vs `margin` | **边界**问「值到了界限会怎样」；**余量**问「离界限还剩多少空间」 | 看输入是**落在界点上**还是**测承载上限** |
| `functional` vs `performance` | **功能**问「做对了吗」；**性能**问「多快」 | 看断言是**结果正确**还是**耗时/吞吐达标** |
| `api` vs 其余 | **接口**问「契约对不对」；其余按业务语义 | 看验证对象是**参数/返回/错误码约定**还是业务行为 |

**判定顺序（命中即停）**：先看有没有明确指标（→ `performance`）→ 再看是不是承载上限（→ `margin`）→ 再看是不是契约（→ `api`）→ 再看是不是界点（→ `boundary`）→ 再看是不是安全属性（→ `security`）→ 都不是 → `functional`。

## functional / 功能测试

**问什么**：业务流程在正常输入下是否得到预期结果。

- 执行方式：**按步骤 `channel` 分**——界面步用 `uia`（UI Automation 读控件树），纯逻辑步用 `runner`（测试代码）。
- 证据来源：`runner+model`（测试代码结果或 UIA 读到的控件属性）；只有肉眼补充的描述性观察才标 `model`。
- 例：登录 → 加购 → 结算 → 订单出现在列表里，金额正确。

**误用**：把「接口返回 200」当功能通过——那是 `api`。把「耗时 80ms」当功能——那是 `performance`。

## performance / 性能测试

**问什么**：在**有明确指标**时验证耗时、吞吐或资源使用。

**关键约束（用户明确要求）**：性能测试**写成测试步骤**，形如「点击某元素，观察耗时多少毫秒」，不要写成一堆压测代码。

```json
{ "no": 2, "action": "点击「结算」按钮", "operation": "点击结算并记录响应时间", "expected": "响应时间 ≤ 2 秒" }
```

- **没有明确指标的「感觉慢」不算性能用例**。指标从哪来：需求文档 / 合同 / 用户口述，写不出来就不要生成。
- 指标必须可判定（`≤ 2s`、`≥ 100 QPS`），不能写「比较快」。

## boundary / 边界测试

**问什么**：输入**落在界限上**时会怎样。

- 典型输入：`0`、`-1`、最大值、空值、空集合、单元素、超长字符串、临界日期（闰年、跨年）。
- 判据：输入本身是**界点值**。
- 例：购物车数量输入 `0`、`999`（上限）、空字符串。

**误用**：把「连续加 1000 次看系统扛不扛得住」标成边界——那是 `margin`。

## api / 接口测试

**问什么**：接口的参数、返回值、协议约定与错误响应是否符合契约。

- 典型断言：字段名、类型、必填性、状态码、错误码与错误文案、幂等性、分页约定。
- 判据：验证对象是**契约本身**。
- 例：`POST /orders` 缺 `items` 时返回 400 且 `code=E_MISSING_ITEMS`。

**误用**：走完整下单链路验证「订单金额算对」——那是 `functional`（业务行为），不是接口契约。

## stress / 强度测试 —— 本轮不测

**用户明确要求**：强度测试暂时放一边，先不测。

**因此：**
- **不要生成 `stress` 用例。** 枚举里留着它只是为了存储和界面枚举完整。
- 不要为了「7 类凑齐」硬造强度用例。
- 不要用 `stress` 去装 `margin` 或 `performance` 的内容。

用户后续明确要求补强度测试时，口径是：验证系统在**超设计负载**下（持续满负荷、资源耗尽、长时间运行）是否仍能保持正确性与可恢复性；判定依据需届时就真实项目确认，不得自行套用。

## security / 安全性测试

**问什么**：安全属性是否成立。

- 典型场景：鉴权与越权（横向/纵向）、注入（SQL/命令/模板）、敏感数据泄露、签名与篡改、越权访问、会话失效。
- 判据：断言的是**安全属性**，不是业务正确性。
- 例：普通用户访问 `/admin/users` 返回 403，且不泄露任何用户数据。

**误用**：把「密码框显示为圆点」标成安全性——那是 UI 功能。

## margin / 余量测试

**问什么**：系统**离承载上限还剩多少空间**。

- 典型场景：容量上限（数据库连接池、队列深度、文件大小、并发数）、持续接近上限时的表现、余量报告。
- 判据：验证的是**离上限的距离**或**逐步加压到接近上限**的表现，不是单个界点值。
- 例：并发从 50 逐步升到 200，记录在 150 时开始出现超时的现象，得出「余量约 3 倍」的结论。

**与 `boundary` 的区别（最容易错）**：

```
输入值 = 999（上限值）        → boundary
并发从 50 加到 200，看何时劣化 → margin
```

**与 `stress` 的区别**：`margin` 是在上限**以内**找余量，`stress` 是**超过**设计上限压到崩。本轮只做 `margin`。

## 生成后的分布自检

生成完用例，按功能项 × 类型统计一次：

- **不要求每个功能项凑齐各类**。按该功能项的实际特性选，硬凑会产出无意义用例。
- `functional` 通常占多数，这是正常的。
- 如果有功能项一个类型都没有 → 漏了。
- 如果 `margin` / `security` 在所有功能项里出现 0 次 → 复核是否本系统确实不涉及；涉及却没生成就是漏了，要在覆盖清单里说明。
- `stress` 计数必须为 **0**。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 用 `stress` 装「压测到崩」的用例 | 本轮不测强度，删除或不生成 |
| 把「输入 999（上限）」标成 `margin` | 那是 `boundary`；`margin` 测的是离上限的距离 |
| 没有定量指标的「响应要快」标成 `performance` | 写不出可判定指标就不要生成 performance 用例 |
| 把业务链路验证标成 `api` | 验证业务行为是 `functional`，验证契约才是 `api` |
| 为了凑类型硬造用例 | 按实际特性选，宁缺毋滥 |
