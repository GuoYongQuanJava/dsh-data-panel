# 异常处置分支：批量「未确认」/家族性失败的诊断与修复

> **什么时候读**：Step 5 执行后出现**成片** `unconfirmed`/`failed`，且怀疑不是被测软件缺陷，
> 而是链路/环境/工装自身问题时，**立刻转到本文件，按 §3 的第 0-5 步判定**。
> 不是每轮都读，只在命中 §2 的触发条件时读。

**主流程（功能项 → 用例 → 步骤 → 执行 → 报告）不变。**
本文件只补「出了问题怎么定位、怎么修、修完怎么回归」这一段。

---

## 1. 问题画像

全量执行后出现**家族性**未确认/失败：一批依赖同一前置（如进入某状态/场景、某门控打开）
的用例全部卡住，典型表象：

- 某门控标志**恒 0** 或某按钮状态**恒不可用**，单步重跑也不变；
- 握手请求类主题（进入/退出/确认）**不出现**或**恒无回执**；
- 失败范围与「同一上游数据依赖」**高度相关**。

这类问题通常不是被测软件缺陷，而是下面四类之一或叠加：

| 类别 | 机理 |
|---|---|
| **① 环境性断链** | 被测服务之间经服务化/私有通道推送的数据，对工装订阅**不可见**，导致被测侧某门控输入在测试环境下恒为初始值（0） |
| **② 测试状态残留** | 某用例注入了被测侧**跨用例常驻**的状态（规则/配置缓存类，直到下次加载才复位），污染了后续所有相关用例 |
| **③ 工装注入自身缺陷** | 「清除/中性」注入的字段值恰好**命中**被测侧门控表/白名单，反而把门永久关死；或注入帧漏设参与匹配的字段，被被测侧按不匹配**静默丢弃**（无任何日志） |
| **④ 预期结果误读源码** | 把相近的定时/清除机制张冠李戴（如把 A 流程的超时定时器当成 B 提示的重发机制），或漏看某分支缺少清除调用，导致预期与真实语义相反 |

## 2. 触发条件（满足任一即读本文件）

- 全量执行后 `unconfirmed`/`failed` **成家族**出现（同一前置、同一场景、同一 topic 相关）；
- 某门控/进入/按钮类断言**连续多轮恒 0 或恒 1**，单步重跑也不变；
- 「注入正常发出、被测侧无反应」且**时间相关性明显**（如某用例跑过后其它用例才开始坏）。

> **硬规则：`unconfirmed` 家族 ≥ 3 条时，禁止直接重跑交差。**
> 必须先走 §3 的 0-5 步判定并留下证据链。重跑一次还是同样的结果，
> 只是浪费一轮执行时间，问题还在。

> **`unconfirmed` 是什么**：跑了但证据不足，**不能判通过，也不能判缺陷**。
> 它不是「失败」也不是「跳过」。详见 [证据链三条硬校验](evidence-chain.md)。
> 大批 `unconfirmed` 通常意味着**工装没取到证**，而不是被测软件错了 ——
> 这个区分决定了后续所有动作的方向。

## 3. 根因分类与判定流程（**先分类，再动手**）

按顺序判定。**每一步都要有总线证据，禁止推测定罪。**

### 第 0 步：建立每 topic 帧计数器（工装必备前置能力）

- 工装订阅表**每条目挂帧计数器**，断言证据里输出 `TOPIC.cnt`。
- 判据三分叉：

| 现象 | 结论 | 下一步 |
|---|---|---|
| `cnt == 0` | 该 topic **根本没到你的订阅口**（断链 / 未匹配 / 通道不可见） | 走第 1 步 |
| `cnt > 0` 但字段恒 0 | 上游没发内容，或**解码/字段错位** | 查解码与 ICD |
| 字段有值但门不开 | 传输没问题 | **去读被测源码的门控条件** |

- **纪律：没有计数器证据之前，不要给任何环节定罪。**
  传输日志/控制台里「发送成功」与订阅端计数要**互相印证**，
  任何一方单独出现都不足为凭。

### 第 1 步：区分「环境断链」vs「工装看不到」

- 被测服务之间的服务化/私有通道流量，对工装订阅**往往不可见**：
  **工装侧 `frames=0` 不是断链证据**。
- 判定方法：读被测源码，找到该门控输入的**最终来源 topic**；
  若来源是服务化推送（工装订阅列表里没有，或恒 0），按**环境断链**处置 ——
  工装直接向该 topic 注入等价健康帧（**feed 仿真**），把上游依赖收敛进环境基线：

```
/* 门控输入来自服务化推送、工装不可见时：
   按源码门控逐项构造满足条件的健康帧，周期注入 */
upstreamTopic.fieldA = <门控要求值>;
upstreamTopic.fieldB = <门控要求值>;
addInj(topic, &upstreamTopic, periodMs);
```

- **feed 的字段必须逐项对照源码门控取值**，不能凭感觉给默认值。
- **feed 帧本身也要进入环境基线**（每条相关用例的前置都注入），
  **不依赖别的用例顺手发** —— 那会把用例顺序变成隐式依赖。

### 第 2 步：排查「状态残留 / 用例污染」

**特征**（三条同时成立基本可确诊）：

- 某用例跑过之后，后面某家族**全部变坏**；
- **单跑**后面用例也坏；
- **全量首跑**该家族反而好。

**判定**：读被测源码找**常驻状态**（规则库/配置缓存、加载结果、进入标志等
「直到下次 X 才复位」的变量），对用例顺序定位**是谁写坏了它**。

**修复：前置自复位** —— 每个依赖该状态的用例 `setup` 里把状态重置回已知基线
（重新加载默认配置 / 显式复位），**不依赖用例执行顺序**：

```
/* 依赖常驻配置的用例，前置统一重新加载默认值 */
reloadDefaultsToKnownBaseline();
```

> **通用规则：凡「被测软件会跨用例常驻的状态」，都必须写进每条相关用例的前置条件**
> （用例文本层的 `precondition` 也要写明，不能只写在测试代码里）。

### 第 3 步：审查工装注入帧本身

- 每个「清除/复位/中性」注入，必须**对照被测源码的表/枚举/白名单**核对字段值：
  你选的「良性值」可能恰好是**门控表的键**，注入反而把门永久关死。
- **每帧所有参与匹配的字段都要设全**：漏一个匹配字段，被测会**静默丢弃且不记日志**，
  表现为「注入正常发出但被测无反应」。
- **修法定向**：清零/清除类注入**优先用空表/零计数帧**，
  而不是「挑几个看着无害的值」。
- **关键注入后立刻验证「已生效」**：用被测侧可观测的回执（状态字、计数、日志行）确认，
  **未生效不进下一步断言**。

### 第 4 步：复核预期结果是否读漏源码分支

- 每条「自动清除 / 超时重提 / 恢复后自动复位」类预期，
  **必须在被测源码里找到确切的调用点（函数名 + 行号记入用例备注）**；
  **找不到调用点就把预期改成「不自动清除，需 X 操作清除」**。
- 常见误读模式：

| 误读模式 | 说明 |
|---|---|
| 相近机制的定时器混用 | 把 A 流程的超时定时器当成 B 提示的重发机制 |
| 置了标志但没调清除/发送函数 | 某分支只置位，没有后续动作 |
| 「一次性」门 | 置位后不再重复触发，第二次注入无效果 |

- **预期修正要同步落到用例文本层**（`description` / `expectedResult`），
  报告中如实写「依据源码某处语义修正」，**不留原始误读口径**。

### 第 5 步：工装冷启动 / 事件窗口类偶发

- 新进程启动后 **DDS discovery 需要秒级时间**，首批注入帧可能丢 →
  关键注入前加**预热包**（无害帧 + 短等待），或关键握手用**多次重发循环**代替单次。
- （别的中间件同理：MQ 连接、gRPC 通道就绪都要时间，预热思路一致。）
- 被测软件的**事件型单发帧**（发完即清零）本身有采样窗口风险 →
  断言侧重发循环制造**多个事件窗口**；
  报告里把「事件单发帧窗口内未捕获」标注为**偶发观察缺口**，**不当缺陷断言**。

## 4. 修复后的验证与回归纪律

### 4.1 验证顺序

1. **修复先单步验证**：受影响用例单独跑 **2 次**，确认稳定，再全量重跑。
2. **全量重跑**只在单步稳定之后做。

### 4.2 ★ 版本纪律：**落地前**返工不建新版本

> **本节与主 Skill 的「每次一键执行都新建版本，绝不覆盖旧版本」不矛盾 ——
> 因为「落地」之前的返工，属于**把这一轮做完**，不是「又开一轮」。**

#### 什么叫「落地」

**落地 = 这一轮测试形成了正式结论、可以交给验收方了。**

| 未落地（还在生成/修复窗口内） | 已落地 |
|---|---|
| 执行刚跑完，结果里还有成片 `unconfirmed` 没处理 | 报告已生成并交付/验收 |
| 正在按本文件 §3 定位根因、修工装与前置 | 用户已确认「这版结果可以」 |
| 用例/步骤还在调整，没形成最终数据 | 报告版本已是正式结论 |
| **怎么改都还没形成结论 → 不建新版本** | **再动就是新的一轮 → 新版本** |

#### 窗口内怎么做

**在「未落地」窗口里，发现问题就直接用本文件 §3 的方法修，修完重跑，
沿用同一 `runId` 原地覆盖，不建新版本；执行记录每用例一条，不堆叠。**

```
① 一键执行 → 结果成片 unconfirmed
② 判定：这一轮还没落地（结果不可用，本来就要返工）
③ 按 §3 第 0-5 步定位根因 → 修工装/前置/注入帧/预期
④ 同 runId 原地重跑覆盖 → 修到全部有明确结论
⑤ 报告生成、交付 → ★ 这一刻起才算「落地」
```

**「修复执行好后就落地了」** —— 修完、结论齐了、报告出了，才是落地。
落地之后再要动，就必须按主 Skill 走：**新 `runId` + 新报告版本**。

#### 为什么这样定（实测来由）

2026-11-24 实测：一键执行跑完，一大批用例是 `unconfirmed`。
**这些结果本来就不能用**，只能返工。返工要是不算同一轮，就会在版本历史里
留下一堆「未确认」的废版本 —— 报告页被无效版本挤满，反而看不清真正有效的结论。

`unconfirmed` 的本质是「**没取到证**」，不是「测出了失败」。
在还没落地的时候把它修掉，是**把这一轮做完**；
落地之后再修，才是**新的一轮**。

#### 反向约束：不许拿这条当借口

| ❌ 错误用法 | 为什么不行 |
|---|---|
| 已经出了报告、交给用户看了，发现要补用例，还用同 runId 覆盖 | 那是新的一轮，旧结论已被采用过，必须留痕 |
| 被测软件改版了，还沿用同 runId | 被测对象变了，不是同一轮 |
| 用户加了新用例 / 重新生成了步骤 | 用例与步骤内容变了，不是同一轮 |
| 把「修工装」当成「改被测软件」的理由反复重跑 | 修工装可以；被测改版必须新版本 |

> **一句话判据**：
> **「这一轮的结果有没有被当成正式结论交付出去？」**
> 没有 → 随便修，不建版本。有了 → 一律新版本，绝不覆盖。

### 4.3 覆盖链路必须整条跑完

```
结果布局修正 → 数据契约检查 PASS → 执行记录重建
   → 报告重新生成 → 版本目录原地覆盖
   → 面板/接口验证（activeVersion、分组数、记录数、report.runId 对齐）
```

**契约检查必须 PASS 才能进报告**：

```
python <插件包>/assets/report/check_contract.py --root <项目>/.dsh/test-sessions/<SID>/integration --run <runId>
```

### 4.4 报告备注要分层写根因

按实际类别写，**不混写**：

| 根因类别 | 报告里怎么写 |
|---|---|
| 环境断链 | 写「已通过 feed 收敛上游依赖」，说明注入了哪个 topic 的等价健康帧 |
| 状态残留 | 写「已改为前置自复位」，说明复位了什么状态 |
| 工装注入缺陷 | 写「注入帧已按源码白名单修正」 |
| 预期按源码修正 | 写「依据源码 `<文件:行号>` 语义修正原预期」 |
| 偶发观察缺口 | 标注为**观察缺口**，不计入缺陷 |

> **两条红线**：
> **① 不把工装修复伪装成被测通过**（那是造假）。
> **② 不把环境断链记成被测缺陷**（那是冤枉）。

## 5. 应当固化进日常流程的条款

下面这些不属于「异常处置」，而应该**在正常流程里就做到**。
已经写进主 Skill 的部分标注了位置，其余需要你在生成/执行时主动遵守。

| 条款 | 落在哪 |
|---|---|
| 工装模板必须内置 **per-topic 帧计数器**与 topic 健康证据输出，作为步骤断言的一部分 | [zzkz-sim/observation.md](../zzkz-sim/observation.md) |
| **预期含「自动/超时/恢复」语义时，必须附被测源码调用点（文件+行号）**；无调用点不得生成自动语义预期 | 本文件 §3 第 4 步 + Step 1 生成用例时执行 |
| **前置条件必须重置被测侧跨用例常驻状态**；不得假设用例顺序安全 | 本文件 §3 第 2 步 + Step 3 生成步骤时执行 |
| **`unconfirmed` 家族 ≥3 条时禁止直接重跑交差**，必须走本文件 §3 | 本文件 §2 |
| **清零/中性注入帧必须对照被测白名单核对**；所有参与匹配字段逐一设值；注入后先验证生效再断言 | 本文件 §3 第 3 步 |
| 修复性重跑覆盖**同 runId 与同版本号**，执行记录一用例一条 | 本文件 §4.2 |
