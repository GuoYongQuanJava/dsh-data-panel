# 功能项覆盖清单

Step 1 产出功能项时同步产出。本清单用于暴露**遗漏的功能项与遗漏的场景**，不等同于覆盖率收集器的行/分支数据。

## 核心前提：模型生成的功能项不许留空（先读这条）

**`source` 不是 `manual` 的功能项，必须至少有 1 条用例。** 模型自己立了项却 0 条用例，
在报告里会变成空章节，还会生出「设计了 0 个用例」这种自相矛盾句。

所以本清单的 `items[]` 装的是**本轮真正立了项、也真有用例的功能项**。

**★ 例外：`source: "manual"` 的功能项允许 0 条用例。**
那是用户在面板侧栏点「＋ 新建功能项」手动加的，面板写入形态是 `{ id, name, source: "manual" }`，
没有 `code`、没有 `stage`、0 条用例 —— **这是面板既有行为，不是脏数据**。
模型**不要删、不要当错误报**；可以补 `stage`/`code`，但补之前先告知用户。

**想表达「这个能力我看到了，但本轮故意没测」，写到 `excluded[]`，不要塞进 `items[]`。**

```
items[]     = 本轮立项的功能项，必有 caseIds（非空）
excluded[]  = 本轮不立项的能力，必有 reason（可复核）
manual 空项 = 用户手建，允许 caseIds 为空，模型不动
```

## 为什么要单独做清单

只列出「我决定测的功能项」，事后没人能判断还有多少没测。清单的作用是把**没测的也写下来**，让缺口可见、可审。

## 与单元测试范围清单的关系

**借鉴思路，不共用实现。**

- 单元测试有 `lib/scope.js`（扫描源码文件、算哈希、`status: tested/excluded/declaration/deferred`）。
- 集成测试的度量单位是**功能项**，不是源码文件，所以**独立写一份**，语义从「源码文件」换成「功能项」。
- **不要 import 或修改 `scope.js`**，也不要把集成测试的清单塞进单元测试的 `testScope`，会污染单元测试行为。

## 清单格式（version 2）

写到 `<项目>/.dsh/test-sessions/<SID>/integration/case-versions/<V>/coverage.json`。

```json
{
  "version": 2,
  "generatedAt": "2026-11-24T09:00:00+08:00",
  "caseVersion": "V0.0.1",
  "sourceBasis": "requirement | skill | code-derived",
  "items": [
    {
      "featureId": "ft_001",
      "name": "商品与购物车",
      "source": "requirement",
      "code": "F-001",
      "caseIds": ["V0_0_1-IT-001", "V0_0_1-IT-002"],
      "typeCoverage": ["functional", "boundary", "api"]
    }
  ],
  "excluded": [
    {
      "code": "F-002",
      "name": "订单退款",
      "stage": "第二阶段",
      "reason": "退款依赖第三方支付沙箱，本机无凭据",
      "proof": { "note": "项目 .env.example 中无 PAY_SANDBOX_* 配置项" }
    },
    {
      "code": "F-003",
      "name": "优惠券叠加",
      "stage": "第二阶段",
      "reason": "需求文档标注「待确认」，规则未定稿，等用户确认后补"
    }
  ]
}
```

## `items[]` 的硬约束

| 规则 | 说明 |
|---|---|
| `featureId` 必须对应 `features.json` 里真实存在的 `id` | 挂不上就是孤儿 |
| **`caseIds` 必须非空（`source` 不是 `manual` 时）** | 模型建的空功能项禁止；要么补用例，要么挪到 `excluded[]` |
| **`caseIds` 允许为空（`source` 是 `manual` 时）** | 用户手建的，尊重原样，不要删也不要报错 |
| `typeCoverage` 必须非空（`caseIds` 非空时） | 与 `caseIds` 对应；为空说明数据矛盾 |
| 每个 `features[].id` 都必须出现在 `items[]` 里 | 漏了就是隐藏缺口（`manual` 的也要登记，只是 `caseIds` 可为空） |

## `excluded[]` 的硬约束

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 能力名称 |
| `reason` | ✅ | **必须可复核**，见下节 |
| `proof` | 建议 | 真实探针证据（命令、退出码、日志位置） |
| `code` / `stage` | ❌ | 有就填，便于追踪来源 |

**`excluded[]` 不产生报告章节、不进覆盖率分母、不影响任何报告数字。** 它只是「我确实看过这个能力」的留痕。

## `excluded` 的理由必须是真的

**不允许只写「太复杂所以不测」「依赖外部系统所以不测」。** 这类理由无法验证，等于没写。

理由要能被第三方复核，例如：

```
✅ "退款依赖第三方支付沙箱，本机无凭据（见 .env.example 无 PAY_SANDBOX_* 配置）"
✅ "该模块源码标注 @Deprecated 且构建时被 profile=legacy 排除"
❌ "依赖支付系统，无法测"
❌ "比较复杂"
```

有真实探针证据时记进 `proof`。**不要伪造命令或退出码来充证据。**

## `typeCoverage` 的用处

记录 `items[]` 里每个功能项实际覆盖了哪几类。交付前用它回答：

- 某个功能项 `typeCoverage` 为空 → 数据矛盾，检查是否漏生成用例。
- 全体功能项的 `typeCoverage` 里 `margin` / `security` 出现 0 次 → 复核是否真不涉及，涉及就是漏了。
- 出现 `stress` → **错误**，本轮不测强度，必须移除。

## 审查时怎么汇报（Step 2，不新增确认步骤）

```
功能项清单：立项 8 个，全部有用例（合计 26 条）
  类型分布：functional 14 / boundary 5 / api 4 / performance 2 / margin 1 / security 0
本轮排除：2 个 ← 逐条给理由
  · 订单退款（第二阶段）：依赖第三方支付沙箱，本机无凭据
  · 优惠券叠加（第二阶段）：需求标注「待确认」，规则未定稿
缺口提示：security 覆盖为 0，本系统有鉴权模块，需确认是否本轮补
```

## 冻结与消费

- 生成用例版本时，清单随 `case-versions/<V>/` 一起产出。
- 执行时，本次范围随 `runs/<runId>/snapshot/` 一起冻结。
- **报告取值应消费同一次 run 的快照**，不要读后来被改过的清单。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| **立了功能项但 `caseIds` 是空的** | **报告出现空章节 + 「设计 0 个用例」矛盾句** | **补用例，或删掉该功能项、改登记到 `excluded[]`** |
| 把不测的能力直接删掉不留痕 | 覆盖缺口被隐藏，无法审 | 登记到 `excluded[]` 并给可复核理由 |
| `excluded` 理由写成「依赖库/太复杂」 | 无法验证，等于没写 | 写可复核的具体依据 |
| 伪造探针命令和退出码 | 证据造假 | 没有真实证据就只写文字依据 |
| 把集成清单写进单元测试的 `scope.json` | 污染单元测试 | 独立文件，独立的语义 |
| 改了清单后拿旧 run 的报告 | 报告与数据不一致 | 报告只消费该 run 的快照 |
| 清单里出现 `stress` | 违反「本轮不测强度」 | 移除 |
