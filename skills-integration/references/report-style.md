## 1. 两套报告，绝不能混用

**这是硬性边界，写代码/写脚本前先读这一节。**

| | 单元测试报告 | 集成测试报告 |
|---|---|---|
| 生成器 | `testReport/report-tool/bridge.py` + `builder.py` | `integrationReport/integration_report.py` |
| 入口函数 | `bridge.py` 的命令行 / `cmd.py` | `build_single_step()` / `build_full()` |
| 数据来源 | `result.json` 的 `tests[]`（逐测试函数） | `steps[]`（逐步骤）+ 快照用例 |
| 关键字段 | `scope`、`coverage`、`complexity`、`testFunc` | `stepVersion`、`caseVersion`、`caseCode`、`stages` |
| 模板 | 单元测试报告模板 + 覆盖率/圈复杂度章节 | 配置项测试报告模板（1 范围…附录 A/B） |
| 表格形态 | 按测试函数一行 | 单用例 16 行表 + 阶段分章 + 附录问题单 |

**绝对不要做的事**：

- ❌ 拿 `bridge.py` / `report-tool/` 生成集成报告
- ❌ 把集成数据（`steps[]`）喂给单元测试的 `builder.py`（字段对不上，直接取不到值）
- ❌ 在集成报告里写覆盖率、圈复杂度、MC/DC、测试函数名 —— 这些是单元测试的指标，集成测试没有
- ❌ 反过来把 `integration_report.py` 的逻辑套到单元测试数据上

**唯一的共用点**是「按 `runId` 定位报告目录 + 用系统关联程序打开 docx」这一条通用约定，
仅此而已。报告**内容**的每一个字都来自各自的生成器。

**为什么强调**：两套报告的章节结构、表格形态、数据模型完全不同。混用会直接产出错报告 ——
例如把集成数据喂给单元测试生成器，会得到一份字段全空、章节对不上的 docx，
而且**不会报错**，很难发现。

## 2. 必须调生成器，不许自己写填表逻辑

**报告生成器**（`integration_report.py`）：**按插件包自身位置定位，不要写死绝对路径**。

查找顺序（与单元测试的 `run_tests.py` 同一套做法 —— 它用
`new URL('../assets/run_tests.py', import.meta.url)` 从包内解析，从不硬编码）：

1. `<插件包>/assets/integration_report.py` —— 随插件分发的首选位置
2. `<仓库根>/integrationReport/integration_report.py` —— 仓库内的开发态位置
3. 环境变量 `INTEGRATION_REPORT_SCRIPT` 指定的路径（特殊情况用）

**面板已经把真实路径回传给你**：`GET /data-panel/integration` 的响应里有
`reportScript` 字段，直接用它，别自己拼路径：

```python
# 优先用面板给的 reportScript；拿不到才按上面的顺序自己找
PROTOTYPE = PANEL_REPORT_SCRIPT or find_report_script()
```

> 为什么不写死：这条路径原来固定写成**某台机器上的绝对路径**，别人 clone 到别的盘就失效 ——
> 而下面第 3 条又要求「缺失必须报错不许降级」，于是换台机器报告直接生成不出来。
> **根因是路径写法，不是生成器本身。**

它对外只有两个函数，**报告一律从这里出**：

| 用途 | 函数 |
|---|---|
| 单条用例报告 | `build_single_step(template: Path, data: dict, out_path: Path)` |
| 整项目总体报告 | `build_full(template: Path, data: dict, out_path: Path)` |

**调用方式**（不要重新实现）：

```python
import importlib.util
from pathlib import Path

# PROTOTYPE 来自面板的 reportScript，或按上面 1/2/3 的顺序找到
spec = importlib.util.spec_from_file_location("ir", PROTOTYPE)
proto = importlib.util.module_from_spec(spec)
spec.loader.exec_module(proto)

proto.build_single_step(Path(TEMPLATE), data, Path(out_path))
```

### 2.1 三条铁律

1. **不许自己实现表格填充**。
   原型里包含了全部排版规范（不要章节号、测试类型映射、一页显示、人员默认值、问题单编号…）。
   自己写一套必然漏掉其中几条 —— 已实测踩过：单条报告套了整本模板、测试类型全写成「黑盒测试」。

2. **不许把原型复制一份改**。
   复制出去改 = 规范分叉，以后改了原型那份不跟随。**要改就改原型本身**。

3. **报告生成器缺失时明确报错，不许降级**。
   ```
   报告生成器缺失：<按上面 1/2/3 都找不到 integration_report.py>
   请确认该文件存在（它随仓库分发，见 integrationReport/README.md）；
   或用环境变量 INTEGRATION_REPORT_SCRIPT 指定路径。
   不要在缺生成器的情况下自己实现报告生成。
   ```
   不许静默退回「自己写个简单版」——那样出来的报告不符合规范，而且没人会发现。

### 2.2 推荐做法：直接用 `bridge.py`，不要自己写转换脚本

仓库里已经有**数据转换层**，与单元测试的 `testReport/report-tool/bridge.py` 是同一个分工：

```powershell
cd <仓库根>\integrationReport
python bridge.py --session-root <会话>\integration `
                 --run-id <本次 runId> `
                 --project-code <项目缩写> `
                 --software-name "<软件名>" `
                 --software-version <版本> `
                 --report-version <面板分配的版本号>
```

它负责：读步骤/快照/执行结果 → 写 `report-plan.json` + `report-data.json` → 调生成器出 docx。

**两步分工（与单元测试一致）**：

```
steps.json + cases.snapshot.json + runs/<runId>/{result,observations}.json
        ↓  bridge.py                   ← 数据转换（本步可复核、可倒查）
report-plan.json + report-data.json
        ↓  integration_report.py       ← 填表排版
总体报告 + cases/*.docx
```

**为什么不要再自己写转换脚本**（这条踩过）：
转换逻辑散落在会话目录的临时脚本里，别人拉仓库后根本没有那份脚本；
而且每次重写都容易错字段（已踩过：`result.json` 的步骤号是 `stepNo` 不是 `no`，
写错会让 173 个步骤只匹配到 74 条证据、结论全变成「未执行」）。

自建脚本只在 `bridge.py` 不够用时才写，职责仍然只有「取数据 + 调生成器」：

```
读 steps.json / cases.snapshot.json / observations.json
        ↓
组装成原型要的 data 结构
        ↓
调 build_single_step / build_full
```

**填表、合并单元格、勾选框、分页控制全部由原型负责**，脚本里不该出现这些。

### 2.3 数据来源与结论标注

**只认快照**：`cases.snapshot.json`（生成步骤时冻结的用例）与 `runs/<runId>/snapshot/`，
**不读当前用例版本**。这样即使用例后来被改得面目全非，报告依然可复现。

- 结论粒度是**一个步骤一条**（不是一条用例一条）
- **必须标注结论来源**：`runner+model`（5 类，代码真跑过 + 模型补充观察）与
  `model`（功能测试，只有模型记录），两者视觉上要能区分，不混成一类可信度
- 报告里**不出现测试代码、测试函数名、codeRef**

## 3. 两种报告：取模板的不同范围

两类报告**用同一份配置项测试报告模板**（`配置项测试报告模板.docx`），区别只在**取模板的哪一部分**：

> **模板随仓库进库**（`integrationReport/配置项测试报告模板.docx`，90 KB），
> 克隆后直接可用 —— 与单元测试的 `testReport/templates/单元测试报告模板.docx` 一致。
> 查找顺序：命令行参数 → 环境变量 `INTEGRATION_REPORT_TEMPLATE` → 生成器同目录。
> **不要写死某个机器上的绝对路径**，也**不要**把模板放到桌面等仓库外位置。
>
> ⚠️ 单元测试模板（50 KB）和集成测试模板（90 KB）**不是同一个文件，不能互相替换**。

| | 单条执行报告 | 全部（一键执行）报告 |
|---|---|---|
| 取模板的哪部分 | **只取「4.1.1 测试结果总结」那一张表** | **按配置项测试模板整体编排**（1 范围 … 5 注释 + 附录） |
| 章节 | 不含完整章节结构 | 完整章节；`4.x` 按功能项循环 |
| 触发 | 步骤页某条执行记录点「查看报告」/ 导出 | 报告页，一键执行后生成 |
| 查看 | 开 tab 页（与单元测试一致） | 测试报告页，按功能项分组 |
| 导出 | **单个导出**（与单元测试单条导出一致） | 全部导出（与单元测试一致） |

> 一句话记法：**单条 = 第 4.1.1 节下面那一张表；全部 = 整本配置项测试模板。**

### 3.1 生成器函数与存放位置都不同

| | 单条报告（每条用例一份） | 总体报告（整项目一份） |
|---|---|---|
| 生成器函数 | **`build_single_step()`** | **`build_full()`** |
| 套多少模板 | **只取 4.1.1 那一张表** | 整本（1 范围 … 5 注释 + 附录） |
| 存放 | `reports/<runId>/cases/` | `reports/<runId>/`（与 cases/ 平级） |
| 文件名 | `集成测试报告-<caseId>-全步骤-<版本>.docx` | `集成测试报告-<项目名>-整项目-<版本>.docx` |
| 数量 | 60 条用例 → **60 份** | **1 份** |

**最容易犯的错**：用 `build_full()` 给每条用例生成单条报告 —— 结果是 60 份 70KB 的整本报告，
而不是只含一张表的短报告。**单条报告必须用 `build_single_step()`。**

## 4. 单条报告：一张表，不要章节号

单条报告**不生成完整报告文档**，只保留模板里 4.1.1「测试结果总结」那张表并填好。

**★ 不要章节标题和表题**（用户明确要求，已踩过坑）：

- ❌ 不要 `4.1 用户注册与登录` 这类功能项章节号
- ❌ 不要 `4.1.1 测试结果总结`
- ❌ 不要 `表1 标识 V0_0_1-IT-002 第 1-3 步` 这类表题文字

**单条报告 = 标题 + 一张填好的表**，别的都不要。章节号是整本项目报告才有的东西。

**★ 整表落在一页**：给每一行加 `cantSplit`（行内不断页）+ 除末行外加 `keepNext`（与下行同页），
避免一张表被切成两页。

### 4.1 测试类型 vs 测试方法（两个不同的格，别写成一个）

| 格 | 填什么 |
|---|---|
| **测试类型** | **按用例自身的 `type`**：功能测试 / 接口测试 / 边界测试 / 性能测试 / 安全性测试 / 余量测试 |
| **测试方法** | 固定写「黑盒测试」 |

**常见错误**：两格都写「黑盒测试」。黑盒测试是**方法**，不是**类型** —— 接口用例的类型必须是「接口测试」。

### 4.2 人员与问题单的暂定值

| 字段 | 现在写什么 |
|---|---|
| 设计者 / 校对者 / 测试人员 | **`admin`**（还没有规范，暂定） |
| 软件问题单编号 | **`无`** |

> 这两条是用户明确交代的「先这样」，等有规范了再改。

### 4.3 必须列出整条用例的全部步骤

即使本次只执行了其中一步，**整条用例的步骤都要列出来**：

```
人员三字段：现在暂定都写 admin
功能项：{ code, name }
用例：{
  caseId, title, type, requirement, description, precondition, executedAt, outcome,
  steps: [
    { no:1, action, operation, expected, observed, outcome },
    { no:2, action, operation, expected, observed, outcome },   ← 本次执行的这一步
    { no:3, ..., observed: "未执行（本次只执行第 2 步）", outcome: "notRun" },
    { no:4, ..., observed: "未执行（本次只执行第 2 步）", outcome: "notRun" }
  ]
}
```

**硬性要求**：

1. **不要只写执行的那一步**。整条用例的步骤都要列出来，未执行的写 `notRun` 并注明原因。
2. 未执行步骤的 `observed` 写「未执行（本次只执行第 N 步）」，不要留空，也不要写「通过」。
3. `outcome` 取值：`passed` / `failed` / `error` / `notRun`（未执行）。
4. 报告里**不出现测试代码、测试函数名、codeRef**。
5. 单用例表是模板表4（**5 列 16 行**），步骤行按实际步骤数**自动增删**（4 步→17 行，2 步→15 行）。

## 5. 总体报告：按阶段分章

一键执行的报告**走完整模板结构**，并且**按测试阶段分章**。这块规则最多，逐条照做。

### 5.1 章节骨架

```
1.范围  → 1.1标识 / 1.2系统概述(表1 软件信息表) / 1.3文档概述
2.引用文档
3.测试结果概述
    3.1 总体评估（★ 按阶段数展开段落，见 5.2）
    3.2 充分性分析 / 3.3 环境影响 / 3.4 改进建议
4.<阶段1名>详细测试结果     ← 每个阶段一章
    N.1 <功能点名称>                ← 每个功能项一节
        N.1.1 测试结果总结          ← 该功能点下**所有用例表**连续列在这里
            表1 标识<用例标识>
            表2 标识<用例标识>
    N.2 <下一个功能点名称>
        N.2.1 测试结果总结
            …
    N.n   遇到的问题                ← 所有功能点之后，n = 功能点数 + 1
    N.n+1 与测试用例/规程的不一致
    N.n+2 回归测试                  ← 章内最后一节
        N.n+2.1 <功能点名>          ← ★ 下面**直接接表**，没有 .1 那层测试结果总结
5.<阶段2名>详细测试结果     ← 结构与第 4 章完全一样
…
注释
附录A 软件问题报告单
附录B 软件问题处理单
```

**章号规则**：第 1 个阶段是 `4` 章，第 2 个阶段是 `5` 章，依此类推（`阶段序号 + 3`）。

### 5.2 3.1 总体评估：按阶段数展开段落

模板里那块是**制式段**，写着「总共有 x 个这样的段」。

- **有几个测试阶段，就复制几段**（2 个阶段 → 2 段）
- 每段填该阶段的数据：用例总数 / 执行数 / 通过数 / 未通过数 / 问题数 / 阶段名
- **最后一段固定**：「经本次配置项测试验证，…软件实现了…」只替换软件名

### 5.3 表2 分布统计（功能项 × 7 类）

| 列 | 规则 |
|---|---|
| 需求功能项 | 生成用例时归类的**功能项名称** |
| **测试功能** | ⚠️ **写成「功能测试」**（模板原文字是错的） |
| 7 类各列 | **没有就写 `0`，不要空着** |
| 测试阶段 | **不能空**，填该功能项所属阶段 |

### 5.4 表3 问题分类统计

- 「合计问题数」**没有就写 `0`**
- 「测试问题归零解决情况」**没有就写 `无`**

### 5.5 表4 测试结果记录单

| 列 | 填什么 |
|---|---|
| 测试阶段 | 该用例所属阶段，**不能空** |
| 功能点名称 | 生成用例时归类的功能项 |
| **详细需求追踪条目** | 用例标识去掉 `-N-Tnnn.CTD` 尾部 |
| **用例标识** | 规范标识（见第 7 节） |
| 结论 | 通过 / 未通过 / 未执行 / 未确认 |

### 5.6 模板里的 `xxx` 一律要换成真数据

模板中的 `xxx` 是**预留占位**，不是要照抄的内容。原型已覆盖：

| 位置 | 处理 |
|---|---|
| 3.1 总体评估 | 每阶段一段，填真实用例数/通过/未通过/问题数/起止日期 |
| 3.1 结尾段 | 软件名换真值；**代码注释率没有测量数据就整句不写**（不编百分比） |
| 3.2 充分性分析 | 用例总数 + 功能项覆盖 x/y；**不凭空写 100% 需求覆盖率** |
| 3.3 测试环境的影响 | 按 `meta.runEnv` 写实际环境，或按 `meta.envImpact` |
| 3.4 改进建议 | 模板固定文案，保留 |
| 附录 A/B | 表格逐格填真数据 |

### 5.7 测试阶段从哪来

| 情形 | 怎么定阶段 |
|---|---|
| **有需求规则文档** | 文档里通常已划分阶段（如「第一阶段」「sprint1」），按文档 |
| **无需求规则文档** | 读代码自己划分（按迭代痕迹、版本提交、模块演进） |
| 用户明确指定 | 按用户说的 |

**一个阶段可以包含多个功能项**（如 sprint1 含「用户注册与登录」「商品浏览」）。

> 阶段必须在**生成用例时**就定好（`features[].stage`），报告侧只做归组，**绝不重新划分**。
> 生成用例时没写 `stage`，整份报告只能退化成「全是第一阶段」，**事后无法补救**。

## 6. 表格与附录排版

### 6.1 列宽固定铺满版心

## 7. 用例标识规范

### 7.1 只认 `caseCode`，绝不用 `caseId` 兜底

报告里所有「测试用例标识」列**只能**出现规范形态：

```
GN-651-JYSG_DM_AUTH_LOGIN-1-T001.CTD
```

**不许**出现 `V0_0_1-IT-001` 这种内部主键 —— 它带版本前缀，肉眼看着就像版本号，
这正是「有的报告标识写得跟版本号一样、有的又对」的根因：

- 生成用例时产出了 `caseCode` → 报告对；
- 某批用例漏了 `caseCode`，旧代码拿 `caseId` 兜底 → 报告里就冒出个像版本号的串。

现在原型里的 `pick_case_code()` 已封死这条路：合法 `caseCode` → 用它；
没有/形状不合规 → **按规范现场生成**；连项目缩写都没有 → 写 `T001` 占位，
**无论如何都不会退回 `caseId`**。脚本侧只需保证每条用例都带 `caseCode`。

### 7.2 格式定义

```
GN-651-JYSG_SRS_UI_TESTING-1-T001.CTD
│   │   │    │   │          │ └─ 顺序号 T001、T002…
│   │   │    │   │          └─── 1=正常用例  2=专门测异常情况的用例
│   │   │    │   └────────────── 需求文档章节英文名；无需求文档用功能点英文名
│   │   │    └────────────────── SRS=按需求规则文档 / DM=按代码归纳
│   │   └─────────────────────── 项目缩写（如 肌颜时光 → JYSG）
│   └─────────────────────────── 固定 651，不变
└─────────────────────────────── 测试类型缩写
```

**测试类型缩写对照**：

| 类型 | 缩写 |
|---|---|
| 功能测试 | `GN` |
| 接口测试 | `JK` |
| 安全性测试 | `AQ` |
| 性能测试 | `XN` |
| 边界测试 | `BJ` |
| 强度测试 | `QD` |
| 余量测试 | `YL` |

**最后一段 `.CTD` 固定不变**。

**详细需求追踪条目** = 用例标识去掉 `-1-T001.CTD`：

```
用例标识：          JK-651-JYSG_DM_API_TESTING-2-T002.CTD
详细需求追踪条目：  JK-651-JYSG_DM_API_TESTING
```

**生成时机**：生成用例时**每条用例当场生成**，存进 `caseCode` 字段。
内部主键 `caseId` 保持不变（面板、执行记录靠它关联），`caseCode` 只用于报告和界面展示。

### 2.3.1 ★★ 「实际测试结果」这一列写什么（**照着这条，别自创**）

报告用例表第 5 行是「序号 | 输入步骤 | 预期结果 | **实际测试结果**」。
这一列的内容**完全来自 `steps[].observed`**，`integration_report.py` 不会补任何智能文案
（填空时只会写「未记录实际值」，那是**兜底**，不是合格值）。

**要求：写真实返回值。** 具体到接口/字段/数值，让验收方不看日志就知道跑出了什么。

| 场景 | ✅ 合格 | ❌ 不合格 | 为什么不行 |
|---|---|---|---|
| 通过的接口步骤 | `{"code":0,"data":{"id":1379,"phone":"199****8888"}}` | `断言全部通过` | 没告诉人返回了什么 |
| 通过的接口步骤 | `HTTP 200，code=0，data.list 长度 12，首条 id=262` | `接口返回与落库字段均符合预期` | 全是断言结论，不是数据 |
| 通过的落库校验 | `SELECT 返回 1 行：IsLock=0，YongHuId=1379` | `断言全部通过` | 没给查询结果 |
| 失败的步骤 | `HTTP 409 {"code":409,"msg":"旧会员等级已停用，请使用团购开团授权"}` | `实际结果与预期不符` | 你没写他错在哪 |
| 异常 | `KeyError: 'orderId'，响应体 {"code":0,"data":{"list":[]}}` | `断言未通过` | 缺异常类型和现场数据 |
| 未执行 | `未执行（本次只执行第 3 步）` | `无` | 要能区分「没跑」和「跑了没问题」 |
| 确实没采到 | **留空** | `断言全部通过（接口返回与落库字段均符合预期）` | 用套话遮住「没采集」 |

**三条硬规则**：

1. **通过路径也要写值** —— 这是最容易漏的。「通过」只说明断言成立，不代表读者知道读到了什么。
2. **禁止固定话术**。以下这些一律视为「没有记录」：`断言全部通过`、`实际结果与预期一致`、
   `符合预期`、`测试通过`、`无异常`、`一切正常`、`实际结果与预期不符`。
   `bridge.py` 的 `is_boilerplate_observed()` 会**主动丢弃**它们，然后报告里显示空。
3. **没采到就留空，不要编**。留空显示「未记录实际值」→ 你能发现并去补；
   写一句套话 → 问题被永久掩盖，没人会再查。

**怎么让真实值进得来**：测试代码必须打印 `ACTUAL` 标记。

```python
# Python
print(f"ACTUAL[{case_id}]: {result!r}")
```

```javascript
// JS / TS
console.log(`ACTUAL[${caseId}]:`, JSON.stringify(result));
```

`run_tests.py` 会把它收进 `result.json` 的 `tests[].actual`；
没走 `run_tests.py` 的话，`bridge.py` 也会从 `run.log` 与 `junit.xml` 里捞 `ACTUAL[...]`。
**两条路都没捞到就说明测试代码没打印** —— 去补打印，不要手填套话。

> **2026-11-24 实测事故**：243 个步骤里 180 个的 `observed` 是
> 「断言全部通过（接口返回与落库字段均符合预期）」，来自模型自写转换脚本的硬编码。
> 结果整列 180 行一模一样，用户的原话是「应该为真实输出的数据，
> 而不是一句与预期不符或者未记录实际值」。

报告用例表的「备注信息」栏要能看到「每一步点了什么」以及「点完界面长什么样」。

生成器（`integration_report.py` 的 `fill_remark_cell`）已经实现，**不要手写**。
它按下面规则产出：

```
备注信息 | 1. 点击进入「结算页」
         |    [截图 V0_0_1-IT-001-step-1.png]
         | 2. 点击切换到「待付款」
         |    无截图                          ← 这步缺图，明说
         | 3. 点击「确认支付」
         |    [截图 V0_0_1-IT-001-step-3.png]
```

| 规则 | 说明 |
|---|---|
| **图片来源** | 该步骤的 `steps[].evidence[]`（`bridge.py` 会解析成真实文件，解析不到就丢） |
| **排版** | 一个单元格内纵向段落：`序号. 输入步骤文字` → 下面紧跟该步截图 |
| **图片宽度** | 固定 **10cm**（备注格宽 11.3cm，留内边距）；**高度按原图比例自适应** |
| **某步没截图** | 文字下面写一行 **`无截图`** —— 留痕要求下「没有」本身也是信息，<br>让人一眼看出该步缺证据，而不是以为排版漏了 |
| **整条用例都没截图** | 保持原来的「无」（不写一堆「无截图」） |
| **图片路径失效** | 跳过该图，该步按「没截图」处理（写「无截图」），不留破图占位 |

**所以你能控制的只有一件事：执行时把截图存对地方。**

| 要求 | 值 |
|---|---|
| 存哪 | `<SESSION_ROOT>/runs/<runId>/shots/` |
| 文件名 | **`<caseId>-step-<N>.png`**（必须带 `caseId`，否则同 run 内多用例互相覆盖） |
| 记进 | 该步 `evidence[]` 写 `shots/<caseId>-step-<N>.png`（相对 run 目录即可） |

> **截图是留痕，不是判据**：`outcome` 仍由 `verify_state` 决定，两者都要有。
> 截图失败就留空 `evidence`，不要编路径 —— 报告会自动降级成只有文字。

### 5.8 ★★ 标题必须能被 Word 导航窗格识别（`outlineLvl`）

**用户明确要求（2026-11-20，2026-11-25 复现）**：报告打开后，Word 左侧「导航窗格」
要能看到完整的章节树，点一下就能跳转。

**做法**：不给标题套 Word 内置「标题 1/2/3」样式，而是**直接给段落写 `w:outlineLvl`**
—— 因为模板全是 `Normal` 样式，一挂内置标题会带出 `numbering.xml` 的
`numId=3` 自动编号，章节号变成 `1.`、`1.1`、`1.1.1` 的双重编号。

```
一级标题（1.范围 / 附录A…）  →  <w:outlineLvl w:val="0"/>
二级标题（1.1标识）          →  <w:outlineLvl w:val="1"/>
三级标题（4.1.1测试结果总结） →  <w:outlineLvl w:val="2"/>
```

#### ★ 极易踩的坑：`w:pPr` 子元素顺序错了，`outlineLvl` 会被 Word **静默忽略**

**2026-11-25 实测事故**：报告里 53 个标题段落**都写了** `<w:outlineLvl>`，
但 Word 导航窗格**一个标题都不显示**。查下来是 `pPr` 里元素顺序违反 OOXML schema。

```
❌ 错误顺序（python-docx 的 makeelement + append 总是追加到末尾）：
   <w:jc>  <w:rPr>…</w:rPr>  <w:spacing>  <w:outlineLvl>

✅ 正确顺序（CT_PPr 规定的相对次序）：
   <w:spacing>  <w:jc>  <w:outlineLvl>  <w:rPr>…
```

**Word 对顺序错误不报错、不提示，直接忽略后面的元素。** 这就是为什么
「XML 里明明有 outlineLvl，界面上却没有目录」。

**修法**：每次改完 `pPr` 后**统一按 schema 重排一遍**（生成器的
`_reorder_ppr()` 已实现），不要靠「记住往哪插」。

**本节相关元素的正确相对顺序**（从前往后）：

```
pStyle → keepNext → keepLines → pageBreakBefore → widowControl → numPr
  → pBdr → shd → tabs → spacing → ind → contextualSpacing → jc
  → outlineLvl → rPr → sectPr → pPrChange
```

#### 怎么验证真的生效（**别只看 XML**）

**读 XML 里有没有 `<w:outlineLvl>` 是不够的** —— 顺序错了它也在。要用 Word 实际解析：

```powershell
$word = New-Object -ComObject Word.Application
$word.Visible = $false
$d = $word.Documents.Open($path, [ref]$false, [ref]$true)
# ★ 读 Range.ParagraphFormat.OutlineLevel，不是 Style.ParagraphFormat
$d.Paragraphs.Item($i).Range.ParagraphFormat.OutlineLevel
$d.Close([ref]$false); $word.Quit()
```

- 返回值 **1/2/3** = 对应级别标题（`10` = 正文，导航窗格不显示）
- **不要读 `Style.ParagraphFormat.OutlineLevel`** —— 那是样式的级别，
  我们没改样式，它永远是 `10`（正文），会误判成「没生效」
> 生成用例时没写 `stage`，整份报告只能退化成「全是第一阶段」，**事后无法补救**。

### 6.3 ★★ 「异常现象描述」/「问题现象描述」写什么

用例表里的「异常现象描述」和附录 A 的「问题现象描述」是**同一个东西**：
不给 `issue.desc` 时，生成器会用**失败步骤的 `observed`** 自动拼
（`integration_report.py` 的 `failed_steps` 那段）。

所以：**`observed` 写得越具体，这两处就越具体；`observed` 是套话，两处必然一起烂。**

| 位置 | 只有步骤号时（❌） | 写清现象时（✅） |
|---|---|---|
| 用例表「异常现象描述」 | `第 3 步：断言未通过` | `第 3 步：PUT /api/admin/users/1379/level 返回 409 {"code":409,"msg":"旧会员等级已停用，请使用团购开团授权"}，预期 code=0` |
| 附录 A「问题现象描述」 | `第 3 步：实际结果与预期不符` | `后台修改会员等级接口对已停用的旧等级返回 409，未按需求描述自动迁移到团购授权，导致运营无法批量升级用户等级` |

**硬要求**：一条异常描述必须回答三个问题，缺一个就是不合格。

1. **在哪**：接口路径 / 表名 / 字段名（不是「第 N 步」）
2. **读到了什么**：真实返回值或实际库值（带具体数据）
3. **差在哪**：预期是什么，实际差在哪个字段（不是「不符预期」）

> `bridge.py` 会自动把失败步骤的 `observed` 拼成 `第 N 步：<observed>`。
> 所以只要 `observed` 合格，这处就自动合格；`observed` 是空的，
> 这里就只剩一句光秃秃的「第 N 步：」，**一眼就能看出没采集**。
