# 功能项生成规范

Step 1 开始时阅读。功能项是集成测试的**分组维度**，也是「覆盖了什么」的度量单位。

## 功能项是什么，不是什么

| 是 | 不是 |
|---|---|
| 需求级 / 业务能力级的独立实体（「商品与购物车」「用户鉴权」） | 源码里的单个函数或类 |
| 用例版本内部的分组维度 | 跨版本共享的全局实体 |
| 用例的必经归属（`featureId` 必填） | 可选的标签 |

**关键**：功能项**属于用例版本内部**，不跨版本独立存在。用例 V0.0.1 和 V0.0.2 各有自己的一套功能项，互不继承。

```
用例 V0.0.1 = { features[], cases[] }    ← 一次生成的完整快照
用例 V0.0.2 = { features[], cases[] }    ← 全新一套，不继承 V0.0.1
```

所以每次生成新用例版本，都要**重新产出这一版的功能项**，不能复用上一版的 `featureId`。

## 三级来源（按优先级，命中即停）

### 1. `requirement` —— 有需求规则文档

**判定**：项目里有需求规格、设计文档、接口文档、验收标准等描述「系统应该做什么」的材料。

**做法**：
- **按文档的章节或业务模块划分功能项**，不要按代码结构划分。
- `code` 填文档里的需求编号（如 `F-001`、`3.2.1`）；文档没编号就留空。
- `name` 用文档里的模块名，不要自己造词。
- `description` 摘文档原文的关键约束，保留可追溯性。

**为什么优先它**：需求文档是唯一能证明「覆盖了需求」的依据。从代码归纳出来的功能项无法证明覆盖了没写进代码的需求。

### 2. `skill` —— Skill 里已定义功能项

**判定**：当前项目有专属 Skill（如某项目的报告 Skill 或业务 Skill），其中已经列好了功能项清单或业务模块划分。

**做法**：直接用 Skill 的定义，`source: "skill"`。不要把 Skill 已定义的功能项重新归纳一遍，也不要改名。

### 3. `code-derived` —— 都没有，从代码归纳

**判定**：既没有需求文档，也没有 Skill 定义。

**做法**：从代码归纳功能项，把用例归成功能项。归纳依据按可靠性排序：

1. **路由 / 控制器入口**（`@GetMapping`、`router.get`、CLI 子命令）：一个入口集群 = 一个对外能力
2. **模块 / 包边界**（`modules/order/`、`services/billing/`）：目录结构通常反映业务划分
3. **对外接口契约**（OpenAPI / proto / 导出的公共 API）
4. **调用链闭合的业务流程**（从入口到持久化的完整链路）

**必须说明归纳依据**：`description` 里写清「由哪些入口/模块归纳而来」，让用户能审。**不能只给一个名字就说完**。

**不能做的事**：
- 不能因为「这个函数好测」就把它立成功能项。
- 不能把单元测试的 `subjectFunction` 直接搬成功能项——粒度差了一个数量级。
- 不能归纳完不写依据，让用户无从审查。

## 字段规范

```json
{
  "id": "ft_xxx",
  "code": "F-001",
  "name": "商品与购物车",
  "description": "商品的浏览、加购、结算",
  "source": "requirement"
}
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `id` | ✅ | 内部唯一，`ft_` 前缀 |
| `code` | ❌ | 需求编号，可空；有就是原文编号，不要自己编 |
| `name` | ✅ | 必填，用业务语言，不用函数名 |
| `description` | ❌ | 可空；`code-derived` 时**应填**归纳依据 |
| `source` | ✅ | `requirement` / `skill` / `code-derived` 三选一 |

## 允许 0 条用例

功能项**允许 0 条用例**——它表达「这个业务能力存在」，不代表本轮一定测它。

但必须在 [功能项覆盖清单](test-scope.md) 中说明这个功能项为什么 0 条用例（未实现 / 暂缓 / 本轮不测），**不能默默留空**。

## 自检（生成后必做）

生成完功能项与用例后，逐条核对：

1. 每条用例都有 `featureId`，且指向本版本内真实存在的功能项。
2. 每个功能项都能回答「它来源是什么」（`source` + 依据）。
3. `code-derived` 的功能项都写了归纳依据。
4. 没有把单个函数当功能项。
5. 0 条用例的功能项都在覆盖清单里有理由。
6. 功能项数量与业务复杂度相称——不要为了「显得完整」造一堆空功能项，也不要一个大功能项装下整个系统。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 按代码目录结构当功能项 | 功能项和需求对不上，报告里无法证明需求覆盖 | 有需求文档就按文档章节划分 |
| 复用上一版本的功能项 `featureId` | 跨版本数据污染，用例归属错乱 | 每个用例版本重新产出功能项 |
| `code-derived` 不写依据 | 用户无法审查归纳是否合理 | `description` 写清归纳来源 |
| 把 `subjectFunction` 当功能项 | 粒度错误，功能项数量爆炸 | 功能项是业务能力级，不是函数级 |
| 0 条用例的功能项直接消失 | 覆盖缺口被隐藏 | 在覆盖清单里登记并说明理由 |

## ★ 粒度：同类必须合并，不要切太细

**这是最容易做错的一条。功能项是「分组维度」，不是「任务清单」——把同类能力拆成多个功能项，
会让报告出现一堆只有 1-2 条用例的碎章节，读者看不出体系。**

**合并判据（满足任一条就合并）**：

| 判据 | 例子（该合并） |
|---|---|
| 两者的**验证手段相同** | 「SC 数据加载」和「DC 数据加载」都是注入 STA 报文看 `LoadStatus` → 合并成「数据加载握手」 |
| 两者的**被测组件相同**且**判据同一族** | 「雷达科目」「光雷科目」「混合科目」都看 `IU_CMD` + `SAR_SO` → 合并成「传感器科目」 |
| 两者只是**参数不同** | 16 个机动科目不是 16 个功能项，是 1 个功能项下的 16 个参数化用例 |
| 一个是另一个的**子步骤** | 「构建工装」是「执行测试」的子步骤，不单独立功能项 |

**不该合并的（确实要分开）**：

- 被测组件不同，且**判据不同族**（如「场景进入退出」看 `IU_CMD`/`EXP_DIS`，「武器链」看 `FCM`/`SMM`）
- 一个是**基础设施**（启停服务、加载数据），一个是**业务功能**（进入场景、跑科目）—— 层次不同
- 合并后会超过 **40 个可测点**（太粗反而查不动）

**数量由业务能力数决定，没有目标值。**

- **不要为了凑数量而拆分**，也**不要为了好写而合并**。
- 功能项数量 = 这个系统**客观有多少个可独立描述的业务能力**。
  电商系统 10-20 个、嵌入式总线系统 5-8 个、后台管理系统 15-25 个都正常 ——
  **差的是被测系统的复杂度，不是你该写多少**。
- **唯一的下限警告**：若合并到只剩 3-4 个功能项，说明**合并过头了**
  （每个功能项下会堆几十个可测点，查不动、报告章节也失去意义）。
- **唯一的上限警告**：若超过 25 个，检查一下是不是把「一个能力的多种参数」
  当成多个功能项了（那应该在**同一个功能项下**用参数化用例覆盖）。

> ⚠️ **历史坑（2026-11-25）**：本节以前写着「一个中型系统 **4-8 个功能项**比较合适；
> 超过 10 个基本可以断定切细了」。这句话本意是防止切太碎，但**被当成目标值**执行 ——
> 于是每次只出 6-7 个功能项，每个功能项再写 6 条，**总数稳定锁死在 38-42 条**，
> 而实际源码里能枚举出上千个可测点。
> **功能项是分组容器，不是数量指标。决定用例数的是「可测点有多少」，不是「功能项几个」。**

> **实测反例**：曾有版本把「服务启动」「服务存活」「速率基线」「端点检查」拆成 4 个功能项，
> 每个只有 1-2 条用例 —— 报告里 4 个碎章节，读者完全看不出这是一个「基础设施」整体。
> 正确做法：合成一个「服务生命周期与总线」，下面放 5 个可测点。

所以每次生成新用例版本，都要**重新产出这一版的功能项**，不能复用上一版的 `featureId`。

## 功能项与用例必须一一对应：不留空功能项

**硬规则（只约束模型自己生成的功能项）：`source` 不是 `manual` 的功能项，必须至少有 1 条用例指向它。**

```
❌ 错：模型生成 12 个功能项，只有 8 个有用例，4 个光秃秃留着
✅ 对：模型生成 8 个功能项，每个都有 1 条以上用例
```

**为什么模型不许生成空功能项**：

1. 空功能项在报告里会变成**空章节** —— 只有标题、三行「无」、一张用例表都没有，读报告的人不知道这是什么。
2. 总报告会生出**自相矛盾句**：「对…开展了第二阶段测试，共设计测试用例 0 个，共执行 0 个」。
3. 空功能项**不会**带来有效覆盖率信息。覆盖率的分母应由「本轮立项测试的功能项」构成，不是「系统全部能力」。

**要表达「这个能力存在但本轮不测」，正确做法是不立它，登记到 `coverage.json` 的 `excluded[]` 写理由**（见下节），而不是立一个空壳。

**同理，用例不能没有功能项** —— `featureId` 必填，且必须指向本版本真实存在的功能项。

## ★ `source: "manual"` 的功能项允许 0 条用例（用户手工建的）

**这条是上面硬规则的唯一例外，必须分清楚，不要一律当错误处理。**

用户在面板侧栏点「**＋ 新建功能项**」手动加的功能项，面板写入的形态是：

```json
{ "id": "ft_manual_xxx", "name": "用户手动加的名字", "source": "manual" }
```

**没有 `code`、没有 `stage`、0 条用例** —— 这是面板的既有行为，不是脏数据，**不要去「修正」它**。

处理规则：

| 情况 | 怎么做 |
|---|---|
| 用户手建的 `manual` 功能项，0 条用例 | ✅ **允许**，尊重用户的划分，不要删它 |
| 用户手建的 `manual` 功能项，后来在面板上加了用例 | ✅ 正常，`manual` 只是来源标记 |
| 模型发现 `manual` 功能项缺 `stage` / `code` | ⚠️ **可以补，但只补不删**；补之前先告知用户 |
| 模型自己想表达一个能力但没打算测 | ❌ **不许**建成空功能项，登记到 `excluded[]` |

**关键区分**：

```
source = requirement / skill / code-derived  →  模型产出，必须有 caseIds
source = manual                              →  用户手建，允许 caseIds 为空
```

> 判据只有一条：**这个功能项是谁建的**。模型建的就得自己负责给用例，用户建的不归模型管。
>
> `manual` 的存在意义见面板源码注释：它与 Skill 的三种来源区分开，
> 报告侧一眼能看出「这条是人在面板上手动加的」。

## 本轮排除的功能项怎么记（`excluded[]`）

想证明「我知道有这个能力、但本轮故意没测」，登记到 `coverage.json` 的 `excluded[]`，**不放进 `features[]`**：

```json
{
  "excluded": [
    {
      "code": "F-002",
      "name": "订单退款",
      "stage": "第二阶段",
      "reason": "退款依赖第三方支付沙箱，本机无凭据",
      "proof": { "note": "项目 .env.example 中无 PAY_SANDBOX_* 配置项" }
    }
  ]
}
```

- `reason` **必须可复核**，不许写「太复杂」「依赖外部系统」这类无法验证的理由。
- 它只出现在覆盖说明里，**不进报告正文**、不占章节、不影响覆盖率分母。
