# 实际输出 JSON：生成后自检与正式执行后告警

生成测试代码后、进入原有人工审查前阅读。目标是发现缺括号、转义错误、编号写错、非 JSON 数值和输出字段遗漏，不能用预期值替代真实实际值。

## 生成后检查

1. 同一项目复用一个实际输出序列化函数，优先调用项目现有 JSON 库。不要每条用例手拼 JSON 字符串。C++ 若没有现成库，可实现受测的小型序列化辅助函数，但必须正确处理引号、反斜杠、控制字符、Unicode、布尔、null、数字和有限浮点数；不为此默认联网安装依赖。
2. 在独立的序列化自测程序中调用该函数，覆盖上述字符和值，打印 `ACTUAL_JSON[caseId]: {"真实字段名":...}` 单行记录。自测只验证输出辅助函数，不运行被测业务；其合成样本不允许写入正式 run 的 run.log/result.json，不是业务测试证据。自测目录和日志明确标注 `serialization-selfcheck`。
3. 用当前插件包内或会话中同版本的 `assets/run_tests.py` 检查日志：

```text
<DSH Python 3> <runner脚本路径> --check-actual-json <序列化自测日志>
```

如果自测逐条覆盖了当前 cases.json 中的结构化输出，还可加 `--cases <cases.json>`，核对 caseId 和 expectedOutputs 的字段名。没有覆盖全部用例时，不把局部自测说成全量验证。检查命令只读日志，不运行测试、不创建 run。

退出码 0 表示已输出记录符合本次检查要求，2 表示存在问题；根据 issues 中的 caseId、行号和原因修正生成代码并重新自测。缺少编译器、JSON 库或序列化辅助函数而无法完成自测时，在原有审查中明确说明未验证，不宣称自检通过，不绕过授权运行业务测试。检查器不能证明生成源码将来每条运行路径都会正确打印，仍需正式执行证据。

## 正式执行后检查

runner 使用同一严格解析规则：拒绝缺括号、非对象、重复字段、NaN/Infinity 等输出；按本次用例快照检查预期的结构化输出字段。`actualOutputValidation` 写入本次 result.json，具体问题以“实际输出 JSON 告警”写入 run.log。

此告警不改测试断言结果、不中断其他用例，不自动补齐、猜测或复制实际值。测试通过但实际值缺失，必须区分“断言通过”和“实际值未采集/无效”。异常结束前未执行到输出的用例也可能缺字段，分析时解释执行阶段，不把它误判为业务返回空值。

最终对话列出有问题的用例和需要修正的输出代码。按原流程交付报告，缺证据的实际值保留未采集，不能手改 result.json 凑齐。修改测试代码后需要新一次执行才能取得新证据；不要改写旧 run。
